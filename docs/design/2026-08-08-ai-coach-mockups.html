The AI as a coach that can change things

Today the assistant is a bottom sheet with fourteen read-only tools and zero write paths. It can tell you your deadlift has stalled; it cannot do anything about it. This proposes the surface that closes that gap — organised as Adjust, Research and Analyse, where anything that touches your data goes through a confirmation you drive.

Two things already in the app decide most of this design, so it is not a blank page. Goal recommendations (goal_recommendations, statuses pending/applied/dismissed) and the post-workout review (/api/workout-review/…/apply) are both already propose → confirm → apply flows with their own UI. A third pattern invented from scratch would be the wrong outcome; the coach should be the surface those two grow into.

§0

What the coach should be able to do

The planning half of your ask. Grouped by domain, tiered by how hard the change is to unwind.

Three intents, and they are not equal. Analyse reads your data. Research mostly does not need your data at all — it is knowledge, with your numbers as context. Adjust writes. Only the third one needs a confirmation, which is why the sections are worth separating in the first place: it makes the one dangerous verb visually distinct from the two safe ones.

The tier column drives how heavy the confirmation is. A calorie target you can see and re-set yourself in ten seconds does not deserve the same ceremony as a phase change that resets a cycle counter.

DomainWhy it stays read-only
Set logs, workout sessionsEvery analysis the coach gives you is only worth something if it never touched the record it is reasoning from. A coach that can quietly edit yesterday's numbers cannot be trusted about this week's trend.
Sleep, HR, ring and scale metricsDevice-sourced. The ranked per-field merge in lib/data/health-source.ts exists precisely so provenance is tracked; an AI write has no honest rank to claim.

Two engineering constraints that shape the UI, not just the code.

1. The proposal is a structured patch, never prose. CLAUDE.md already requires generateObject with a schema for any LLM call returning structured data, and forbids letting a model-reported number gate an automatic action. So the confirmation screen is not a nicety layered on top — it is the only legal way this feature can exist. The AI fills a typed patch object; the screen renders it; the server applies it.

2. A proposal can go stale between generation and apply. You might edit the program in another tab, or a workout completes and regenerates the prescription. The apply endpoint must re-validate against current state and refuse a patch whose base has moved — the UI needs a state for "this suggestion is out of date, re-ask". Cheap to build now, ugly to retrofit.

§2

The change and the confirmation

Your deadlift-swap example, drawn five ways. This is the part that has to be right.

All five show the same underlying patch so you can compare the containers rather than the content: swap Deadlift for Romanian Deadlift in your Thursday session, at a lower working percentage because the RDL is a different lift.

The thing worth deciding here is how much a confirmation should tell you. The minimum is "old value → new value". What separates a trustworthy version is the second list — what else moves as a consequence. Swapping a lift does not just edit one row: it changes your weekly set count per muscle, it orphans a PR that will now never grow, and it feeds the recommendation engine different inputs. B3 and B5 show that; B1 hides it behind a tap.

§4

Decisions I need from you

Things I would otherwise guess at, where guessing wrong means rework.

  1. Should the coach be able to log things — food, a workout, a body weight? Natural to ask for ("log 200g chicken"), and it would be genuinely useful. But it crosses the line in §0: logs are records of the past, and the read-only argument for records is what makes the analysis trustworthy. My inclination is no for the first version, then revisit — but it is your call and it changes the tool surface.
  2. Route or sheet? The current chat is a 78vh bottom sheet. A confirmation screen with a consequence list wants more height than that, and the day-detail screen set a precedent for real routes. A route also gets you back-button behaviour for free. The cost is that the AI stops being a thing that floats over whatever screen you are on.
  3. Does it get a name? "AI Analysis" is the current header and it is now wrong — analysis becomes one of three things it does. "Coach" is what your description of it kept implying.
  4. How long is the undo window, and is there one at all? Applied changes could be reversible for 24 hours via the stored before-state. It is the single biggest trust lever for tier-3 changes like a phase edit, and it is meaningfully more work than shipping without it.
  5. Does the standing brief (A6) generate on a schedule or on open? There is no cron layer in this app, so "on open, cached for the day" is the realistic answer — worth knowing whether the idea survives that constraint before I design around it.
§5

Where I would land

If you want a starting point rather than a menu.

A2 + A4 for the shell — a launcher that teaches the three capabilities, with steer chips above the composer so the sections stay reachable mid-conversation instead of only at the start.

B1 → B3 for changes, with B2 inline for tier-1. A calorie target should not cost you a screen transition; a phase change should. That split falls straight out of the tier column in §0 rather than being a taste call.

C3 and C4 for analysis, because both end in a button that produces a proposal — which is the entire reason to put analysis and modification behind one surface instead of two.

The piece I would build first is none of the above: it is the typed patch schema and the apply endpoint, with re-validation against current state. Every mockup here is a renderer for that object. Get it wrong and all five B-mockups are wrong with it.
