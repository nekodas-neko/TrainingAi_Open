You said yes to persistence "if it's not too resource intense" — this is the cheap version and the split is the trick. Applied changes are the part with lasting value, and they are already a row in the DB the moment you tap Apply; listing them costs one query and no new storage. Conversations are the expensive part (a table, message rows, a growing blob), so they get a 30-day window and no search. If storage ever bites, drop the bottom half and the top half still answers "when did I change that, and why".

What's left to decide

Three, all small. Everything else is settled.

All three were answered on 2026-08-08 and are recorded here so they are not re-opened.

  1. Pairing default → T2, with T4 for long lists. Fused card for 2–6 items, per-row sparklines beyond that, T3 bar-tapping available for small ranked comparisons. The selection rule lives in the system prompt.
  2. Injury → neither warn nor remove; Coach only writes the record. The owner's answer was that it should behave exactly as manual injury entry does, and that behaviour already exists end to end: signals.ts derives activeInjuredMusclesInSession, the periodization prompt weighs it via session_swap_recommended / deload_recommended, and injurySafeAlternatives drives per-exercise swaps at workout time. Emergency-deload deliberately excludes injuries as a blunt standalone trigger (AI-4) — that comment is a decision, not an oversight. Coach reimplements none of it. D3's second toggle is superseded.
  3. History → both halves. Applied changes (one query, no new storage) plus conversations on a 30-day window with no search. Pruned on write, since there is no cron layer.
