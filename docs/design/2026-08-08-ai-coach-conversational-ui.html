AI Coach — a conversation that renders its own UI

You talk to it normally. When answering would mean typing something it could just show you, it renders a control instead of a question — a list of your sessions, a picker, a dial, a diff. You tap, the conversation moves on. Same thread, no menus, no forms.

Which means the thing to design is not screens — it is a vocabulary of widgets the model can call, plus the rules for how they behave once you have answered. Eight widgets, drawn in §2. The rules are in §3 and they matter more than the pixels: get the resolved state wrong and the thread turns into a graveyard of stale pickers.

§1 is the answer

Your exact example — "I want to change my workout" — walked end to end in eight frames. Read this first; everything else supports it.

Widgets resolve ambiguity

They are not a wizard. Say something specific and it skips straight to the change. F8 shows that, and it is the difference between a coach and a menu.

Typing always works

Every widget has a typed equivalent. The list is an accelerator, never a gate — F3 shows someone ignoring it.

Named AI Coach

Applied throughout. Home button routes to a full page rather than opening the 78vh sheet — reasons in §4.

Session names in these mockups are illustrative. "Upper", "Lower" and "Full Body" are read from the user's active program at render time. CLAUDE.md's rule stands and is load-bearing here: session identity is the DB id, never the name, and the widget's option list is built from program.sessions — there is no fallback array with named content.

§2

The widget vocabulary

Eight components the model can render. Each is a tool call with typed arguments — this list is the actual build spec.

The model does not emit markup. It calls a tool with a typed payload and the client renders a known component — the same discipline CLAUDE.md already requires of structured AI output. That means the widget set is closed and reviewable: an assistant that could invent arbitrary UI could also invent an Apply button that lies about what it does.

Every widget resolves to a value, and every widget's value can also be produced by typing. If you cannot describe a widget's output as a sentence the user could have said, it does not belong in the vocabulary.

§3

Three rules that decide whether it feels like a conversation

Cheap to get right now, structural to fix later.

The widget catalogue is the easy half. What actually separates "chatting with a coach" from "operating a menu" is what happens to a widget after you have used it, and whether the assistant knows when not to render one at all.

The picker vanishes and your choice becomes a normal user bubble. Scroll back a week later and the thread reads as a plain conversation — the UI was scaffolding, and scaffolding comes down. The undo glyph re-opens the picker, so nothing is lost by collapsing. This is the one I would build.

The trigger rule, stated positively. A widget appears where the sentence was genuinely under-specified — "a bit" has no number in it, so it hands you a dial rather than guessing 150 or asking you to type. Say "bump my calories to 2700" and it goes straight to the confirmation. Same intent, different precision, different amount of UI.

The stale-widget problem, which only shows up in a real thread. A picker rendered three turns ago is still on screen and still tappable. If you scroll up and tap it, what happens?

R1 makes this mostly moot — resolved widgets are gone, so the only live one is the newest. But a widget you abandoned (asked something else instead of answering) is still sitting there. The rule I would ship: a widget goes inert the moment a newer turn exists, rendering dimmed with a "no longer current" affordance rather than silently doing something surprising. Same class of bug as the stale-proposal problem from round 1, and it wants the same answer.

§4

Name and entry

Both settled, with the reasoning kept so it does not get re-litigated.

Name: AI Coach. Applied throughout this document. "AI Analysis" was already wrong once analysis became one of several things it does, and every description you gave of the behaviour was a trainer's.

Entry: the Home sparkles button routes to a full page at /coach. You suggested this and it is the right call for three reasons beyond convenience. Widgets need height — the current 78vh sheet leaves roughly 300dp of thread once header and composer are subtracted, and F7's confirmation alone is 260dp. A route gets Android back-button behaviour for free, which matters because a conversation is something you leave and return to. And it gives the thread somewhere to live: a sheet implies disposable, a page implies history.

The cost, stated honestly: the assistant stops floating over the screen you were on. Today you can open it from the workout screen and keep your place. Mitigation is that the coach can deep-link back — the Receipt widget's "Lower updated" is tappable through to the program editor.

The old overlay does not disappear on day one. It is mounted on four screens (home, session-select, stats, done). Retiring it is a separate change, and the two coexisting briefly is fine — the route is the new front door, the overlay stays until its other entry points are repointed.

§5

Still open

Down to three, and the first is the one I would most like an answer to.

  1. Does the thread persist between sessions? Widgets change this question. A chat history is nice to have; a history containing applied changes is closer to a record — "when did I swap that lift, and why" is answerable from the thread and nowhere else. Persisting means a table and a scrollback UI. Not persisting means the receipt is the only trace and it disappears on close.
  2. Can it log things — food, a body weight? Carried over unanswered from round 1. Widgets sharpen it, because a food logger is an obvious and satisfying widget. Still inclined to say no for v1, on the grounds that logs are records of the past and the coach's credibility rests on not having touched them.
  3. Undo window on the Receipt. Minutes, a day, or until the next session that uses the changed program? The third is the most meaningful for training changes — undo stops being available once the change has actually affected a workout — and is not much harder than a timestamp.
§6

Build order

If this is the direction, the first PR is not a widget.

1. The widget protocol. One tool per widget, typed args, a client registry that maps a widget name to a component, and the resolved-value round trip back into the conversation. Every mockup above is a renderer for this. Two widgets are enough to prove it — ChoiceList and ChangePreview.

2. ChangePreview and the apply endpoint, with re-validation against current state so a stale patch is refused rather than silently applied to moved ground. This is the piece that carries all the risk, and it is worth building before there are six widgets feeding it.

3. The /coach route, reusing the existing chat's streaming and the fourteen read-only tools it already has. Analysis and research work on day one because those tools already exist — the new surface just renders their output better.

4. The rest of the vocabulary, one widget per write domain, each landing with its ChangePreview shape.

Round 1's §0 capability map still governs what step 4 is allowed to touch, and its tier column still decides which changes confirm inline and which push a screen.
