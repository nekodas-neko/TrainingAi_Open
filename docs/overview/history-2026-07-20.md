# 2026-07-20 — Phase counting keys off program-session id, not name (WK-15)

**Branch:** `claude/handoff-documentation-w1ud2j` · **Version:** 1.181.1

## What & why

Backlog item 8 (R4), WK-15. `countAllSessionsSinceStart`
(`lib/data/postgres/slices/programs.ts`) counted a program's sessions grouped by
`lower(session_name)`, and all callers looked up by name. So **renaming a training session
reset its phase progress** — a direct violation of the strict "session identity = DB id, never
name" rule. Phase counting is load-bearing (phase ceilings, `completedCycles`, deload timing),
so the reset silently skewed the whole periodization timeline after any rename.

The R4 plan rated WK-15 backlog-note-only because a straight name→id switch "silently drops
legacy null-`session_id` rows' counts, and mixed id/null rows split the count," and the safe
path looked like a risky backfill migration on load-bearing data.

## The fix (no migration)

The risky backfill was avoided. `workout_sessions.session_id` is the stable program-session
link — the config-save path already re-points it at recreated rows, so it survives renames and
edits; only very old logs and every APK-sync-created row (the sync path stamps no
program-session id) carry a null `session_id`.

`countAllSessionsSinceStart` now returns `Map<programSessionId, count>`:

- Rows with a `session_id` count under it directly (stable across renames).
- Legacy null-`session_id` rows are resolved to their current program-session by matching
  `session_name` **within the queried program** — done in JS against a `name → id` map, so a
  duplicate-named session can't fan out and double-count (a SQL join could).
- Rows matching no current session (a renamed-away / deleted session) are omitted — no caller
  ever looks them up (callers only query current sessions, all of which resolve to an id).

All five call sites now look up by id: `workout-data` (×3: single-tab, `?tab=all` batch, and
the single-session helper), `log-exercise`, `daily-digest`, `sync-workout`. The two name-only
callers resolve their input via the active program's session list — `log-exercise` prefers the
payload's `sessionId` and falls back to a name match; `sync-workout` builds a `name → id` map
from `activeProgram.sessions` and keys its running per-session counter by id.

## Tests / verification

- New DB-backed suite `lib/data/postgres/__tests__/count-sessions-by-id.test.ts` (4 cases):
  id-populated rows count under the id; **a rename does not reset the count** (the core fix);
  legacy null-`session_id` rows resolve by name (case-insensitive); unmatched null-id rows are
  omitted and deleted / early-deload rows excluded. Skips cleanly in CI (no `DATABASE_URL`).
- Smoke against the **real seed** (production-shaped, id-populated Push/Pull/Legs history):
  rename Push → "Chest Day", count under the Push id stays **3 → 3** (the old name-keyed path
  would have returned 0).
- Full gate green: lint 0 errors, `tsc --noEmit` clean, **1844 tests pass** (incl. all DB-backed
  integration tests), `pnpm build` clean.

## Not exercised in-sandbox

The four changed HTTP routes were **not** driven end-to-end through NextAuth (the credentials
CSRF/cookie flow isn't practical to script here). The read-path function they all call is proven
against real Postgres including a rename, and the call-site changes are validated one-line
key swaps (tsc + the function contract test). Server-only — no device / native / safe-area /
offline-sync surface touched.

# 2026-07-20 — Secondary effort floor capped at the main's phase effort

**Branch:** `fix/secondary-effort-cap` · **Version:** 1.180.1

## What & why

Fixes a cross-goal regression introduced by the #663 secondary-effort floor. That change
floored a secondary compound's load at the **accessory target RPE** (goal-agnostic, ~RPE 8) so a
light AI pick couldn't slip through at ~RPE 6 (the bent-over-row bug). But the floor was applied
to every goal — including goals whose *main* runs deliberately light in a phase (strength and
power **accumulation** sit near RPE 6 to accumulate volume). There, flooring a secondary at RPE 8
pushed it **above** the main, inverting the role order (secondary harder than primary).

## The fix

In the `role === 'secondary'` branch of
`app/api/ai-periodization/session/[sessionId]/prescribe/route.ts`, the effort floor is now capped
at the main's hardest intended effort for the phase:

```ts
const mainEffortCeil = expectedRpe(primaryZone.pctMax, primaryZone.repMin)
const secondaryTargetRpe = Math.min(accessoryTargetRpe(goal), mainEffortCeil)
```

So a secondary can match — never exceed — the main's effort. Self-adjusting per goal, no
hardcoded goal list:

- **Powerbuilding / hypertrophy / strength+hypertrophy** — main already tops near RPE 8, so
  `min()` keeps the accessory floor. **Unchanged** (the BoR fix still holds).
- **Strength / power accumulation** — main ~RPE 6, so the secondary now tracks the main (~RPE 6)
  instead of being floored to RPE 8. Inversion removed.

## Also

Added `docs/prescription-intensity-matrix.md` — a **read-only** reference table of the engine's
`goal × phase × role → {%1RM, reps, effort}` output, generated by calling the live functions. No
behaviour depends on it; it exists to make the intensity surface auditable at a glance (it was
what surfaced this regression).

## Tests

- `lib/ai-periodization/__tests__/secondary-zone.test.ts` — updated the `secondaryPct` mirror to
  the capped floor; added a regression test that strength/power accumulation secondaries never
  out-effort the main, and one confirming powerbuilding keeps its RPE-8 floor.
- Full suite green (1737 passed), typecheck + lint clean.

## Not exercised in-sandbox

The prescribe route sits behind live Gemini generation + a real session, so it was **not** run
end-to-end here. The change is a deterministic post-AI clamp; the unit test mirrors the route
branch exactly. No device/native/safe-area surface touched (server-only math).

# 2026-07-20 — R-1: native BLE cursor hole-jump race fixed

**Branch:** `claude/handoff-documentation-w1ud2j` · **Version:** 1.181.2

## The bug (deep-review R-1, HIGH — silent data loss)

`OuraRingService.postDrainBatch` runs on a single-threaded `ingest` executor: each drained BLE
history batch is POSTed, then the persisted resume cursor advances via `confirmStored` **only** if
that batch stored. A guard at the top skips later batches once `drainIngestFailed` is set, so "the
cursor never jumps a hole" — the durability contract (CLAUDE.md Oura Direct-BLE; ops matrix I2/I5/I6).

But the flag was **set on the main thread** inside `main.post { drainIngestFailed = true }`, while the
next batch's guard **reads it on the ingest thread**, and it wasn't `@Volatile`. So when batch B1
failed, its flag-set was merely *queued* to the main thread; batch B2 (next on the ingest executor)
ran its guard before the flag landed, POSTed, succeeded, and `confirmStored` advanced the cursor **past
B1's failed span**. That span never re-drains → **silent, permanent loss of one ≤255-event history
batch per incident.** The JS-side guard is disabled on native-ingest APKs, so nothing else caught it.

## The fix

In `postDrainBatch`:
- `drainIngestFailed` is now `@Volatile` (cross-thread visibility: ingest-thread set/read + main-thread
  reset/re-check).
- The flag is set **synchronously on the ingest thread** the instant `postFramesWithRetry` returns null
  — before the `main.post` — so the next batch's guard sees it before it POSTs (the executor is
  single-threaded and ordered, so this is sufficient).
- The success branch **re-checks `drainIngestFailed` before `confirmStored`** (defense-in-depth at the
  cursor-advance site; `confirmStored` itself is untouched, so the legacy JS path is unaffected).

Conservative by construction: once any batch in a drain fails, no batch confirms, so the cursor can
only ever *hold* further back and re-drain (dedup-safe on `(user_id, ring_timestamp_ds, tag, body_hex)`)
— it can never advance past a hole. A rare, benign edge (a straggler from a prior drain flipping the
flag as a new drain starts) causes at most one extra dedup-safe re-drain, never data loss.

## Verification

- `pnpm exec tsc --noEmit` + eslint clean (the JS/TS half: version + changelog).
- Kotlin is **compile-gated by the Android CI job only** — no Android SDK in the sandbox.
- Brace/paren balance checked. Ops-matrix row **I18** documents the failure + fix.

## Owner action (device-only)

Rebuild the APK (`npx cap sync android && ./gradlew assembleDebug`) so the fix takes effect, then

## fix/s2-running-gate — running recovery-gate correctness (v1.178.1)

Stream 2, deep-review batch item **running-gate correctness** — the §E2/§J prerequisite annotated
onto the F3 running-engine Phase-2 backlog entry. Resolves review **E2-4, E2-5, E2-6, E2-7** (and
their §J duplicates **J-3, J-4, J-5**) plus **E2-2**. All in `app/api/running-plan/route.ts` +
`lib/running/recovery-gate.ts` (and `app/api/workout-data/route.ts` for E2-2).

### The gate was advertising protection it didn't deliver
Every finding was a signal that was assembled (with DB cost) but wrong or unread:

- **E2-6 / J-3 — leg-interference anchor.** `hoursSinceLowerBodyStrength` measured hours from the leg
  session to **tonight's midnight** (`todayMid + 86_400_000`), so any leg day before today read ≥24h
  and never tripped the `< 24h` interference gate — the morning-after-leg-day case it exists for was
  structurally unreachable. Now anchored at `Date.now()`.
- **E2-5 / J-4 — "last night's" sleep.** The short-sleep soften read `Math.max(...)` over **every
  night since week start**, so it could only fire on Mondays or after an all-short week. Now fetches
  the yesterday→today window and takes the longest session whose **wake date is today**; absent →
  neutral (null), never softens.
- **E2-4 / J-5 — two dead inputs.** `strain` and `hoursSinceLastRun` were computed but never read by
  `applyRecoveryGate`. Rather than delete, both are now wired to real protection:
  - **Monotony** (not raw strain — `strain = load×monotony` is in kg and not comparable across users;
    monotony = mean/SD is scale-free). A hard run softens when Foster monotony `> 2.0` (the documented
    high-monotony band). The route now passes `monotony`.
  - **`hoursSinceLastHardRun`** replaces the tz-mixed, unused `hoursSinceLastRun`: computed from the
    most recent **completed** interval/tempo/long run, anchored at the run day's local midnight vs now.
    A hard prescription within `< 24h` of the last quality run softens (no back-to-back quality — 80/20).
- **E2-7 — pending rows counted as training.** `runsThisWeek` filtered only `status !== 'skipped'`, so
  a never-run `pending` row (created just by opening the tab) counted toward `easySoFar`/`hasLong` and
  could push the framework to prescribe an interval day as the week's first actual run. Now counts
  only `status === 'completed'`.
- **E2-2 — re-eval dropped the muscleGroups fallback.** Generation time falls back to
  `ex.muscleGroups.map(mg => ({ muscle: mg, role: 'main' }))` for exercises with no `exercise_library`
  assignments; the consumption-day re-eval used `?? []`, so a custom exercise re-evaluated with zero
  assignments and its per-exercise deload silently reverted to full load while still sore. The re-eval
  now applies the identical fallback.

The unused `listActivityLogs` fetch (its only consumer was the dead `hoursSinceLastRun`) was removed.

## 2026-07-19 — AI prescription poll must not be HTTP-cached (v1.173.4)

Follow-up to the v1.173.2 client-fired prescription fix (#652). On-device, the owner confirmed the
prescription now generates (Railway logs: client `POST …/prescribe` → 200 with a real prescription)
and eventually displays "AI Prescription · Accumulation · Auto-applied" — but only **after "some
resets"** (closing and reopening the session).

### Root cause

`/api/workout-data` returned `Cache-Control: private, max-age=30, stale-while-revalidate=60` on
**every** response, including the prescription-pending **poll** (`?poll=1`). The pre-workout screen
polls this every ~3 s for ~30 s to detect the freshly-generated prescription. But the browser
HTTP-caches the first poll's `aiPrescriptionPending: true` response for 30 s and serves it to every
subsequent poll — the entire poll window — so the client never observes the prescription that lands
mid-window (the POST took ~10.6 s in prod) and times out into "couldn't generate." Reopening the
screen after the 30 s cache expired was the only way to see it.

### Fix

`workout-data` now returns `Cache-Control: no-store` when `?poll=1` (a poll checking for a state
change must always be fresh); non-poll reads keep the SWR cache for instant paint. This makes the
prescription appear on its own within a couple of seconds, no resets.

### Verification

Reproduced locally: with an `ai_dynamic` program in the `consumed`/null state,
`GET /api/workout-data?tab=<id>&poll=1` now returns `cache-control: no-store` (was `max-age=30`);
the non-poll read still returns `max-age=30`. After a `POST …/prescribe` (200), the very next poll
returns `aiPrescriptionPending: false` with exercises styled `AI · Accumulation` — i.e. the client
would immediately swap in the AI numbers. `tsc` + eslint clean.

**Device-confirmed** (indirectly): the owner's screenshot shows the prescription applied after the
#652 client-fire fix deployed; this change removes the reopen-to-see delay. The instant-appear
behaviour itself is APK/browser-cache-dependent and best confirmed on the owner's next session open.

## fix/s2-ble-rollup-efficiency — P4 (rollup-efficiency half): bound the BLE rollup + prune hygiene (v1.174.0)

### The blocker that shaped the design (owner-decided: do the complete refactor)
The review's literal C-1 fix ("add a ds cutoff to `rowsByTags`") is **unsafe**: the rollup's
daily-summary path is `computeDailySummaries` (replays the EMA baselines + nHistory forward over the

  writes through the new **window-scoped** `upsertOuraDailySummary` (never deletes older rows). Because
  each metric's baseline is a pure forward fold and the persisted row IS the complete fold state,

- **C-2 — coalesce per-drain + 0x50 trigger.** The rollup was fired on every ~255-event ingest POST

  promptly. `0x50` (MET) added to the trigger tag-set so a MET-only batch no longer leaves
  MET-gated HRV/RHR + daily-summary metAvg + resilience stale.
- **K6 — rollup failure surfaced.** A caught aggregation failure now also calls `reportServerError`

- **H-5 — prune hygiene.** The `oura_accel_chunks` 7-day prune is now throttled + fire-and-forget
  (was awaited on every insert — a transient lock could 500 an accel POST that already stored); every
  fire-and-forget prune `.catch` now logs; module-map §0 gains the missing battery-poll prune row.

## fix/s2-ble-retention — P4b (retention half): per-workout HR snapshot + rr_intervals prune (v1.177.0)

Stream 2, deep-review batch item **P4b** — the retention follow-up to P4's rollup-efficiency half
(`docs/superpowers/plans/2026-07-19-ble-rollup-efficiency-and-retention.md` §4, Design-notes Levers
W + R). Closes review **H-3** (Lever W) and **H-1 / G-6** (Lever R). `body_hex` untouched.

### The problem
Per-workout HR stats (avg/peak BPM, best HRR1, workout HRV) are recomputed **live** from
`oura_heartrate` + `rr_intervals` on every recap view — nothing persists them. So the existing
180-day `oura_heartrate` prune (and the 90-day `rr_intervals` prune added here) **silently erases**
them for any workout older than the window: strap-sourced rows are not re-derivable from anything,
so a >180d recap shows a blank HR card. First real loss ~2027-01 (first BLE-era workout ages out).
Separately, `rr_intervals` had **no retention bound at all** — the one bounded sample series that
shipped (Polar H10, migration 124) with no prune, projected ~150–250 MB/yr growing forever, with a
single live-recompute-only consumer.

### Lever W — durable per-workout HR snapshot (H-3)
- New table `workout_hr_stats` (migration 135): `workout_session_id PK/FK, user_id, avg_bpm,
  peak_bpm, hrr1_best, workout_hrv_ms, readings_count, source, computed_at`. Server-derived Tier-2
  record, not an offline-first sync domain.

  workout to the snapshot scalars. `lib/workout/compute-workout-hr.ts` → `computeWorkoutHr(repo, …)`
  is the **one** path that assembles readings + per-set recovery + rest-window HRV + summary, shared
  by the done-screen route and the backfill so they can't drift.
- `/api/oura/hr-data` now persists the snapshot **fire-and-forget** on any recap with live data
  (COALESCE upsert gated on `readings_count`: a partial mid-drain recompute never clobbers a fuller
  one; a later compute that gained a value fills the gap). When the raw series has thinned, it
  **falls back to the snapshot** — `hasData:false` but `summary.fromSnapshot:true` carries the
  numbers — and fills `workoutHrvMs` from the snapshot when live RR is already pruned (rr dies at
  90d while the HR trace still renders to 180d).
- Admin backfill `POST /api/oura-ble/backfill-hr-stats` (requireAdmin, bounded/resumable, oldest-first)
  materialises snapshots for completed sessions still inside the 180d window that lack one — must be
  run before ~2027-01. `listSessionsMissingHrStats` is the work-list.

### Lever R — rr_intervals 90-day prune (H-1 / G-6)

sole reader (`hr-data`) recomputes a scalar the snapshot already holds; ring-side HRV pipelines read
ring IBI from `oura_raw_samples`, never this table. Module-map §0 prune registry updated.

# fix/s1-food-items-sync-envelope — P1/D-1 CRITICAL: new-food logs never reached the server

**Branch:** `fix/s1-food-items-sync-envelope` · **Deep-review batch Stream 1, Task 1 (P1)** ·
**v1.171.1 (patch — user-visible data-loss bug fix)**

Plan: [`docs/superpowers/plans/2026-07-19-food-items-sync-envelope.md`](../superpowers/plans/2026-07-19-food-items-sync-envelope.md).
Finding: deep review §D (D-1 critical, adversarially verified REAL; D-2, D-5 note). The one CRITICAL
finding in the whole 2026-07-18 audit.

## The bug (D-1)

`lib/sync/mutation-schema.ts` — the push envelope's `domain` enum omitted `'food_items'`, while
`lib/nutrition/log-food.ts` (`logFoodEntries`) queues a `food_items` mutation (client-minted UUID)
*before* the paired `food_logs` mutation for every new food. On the S25 APK the local-store branch
runs **even when online**, so: `POST /api/sync/push` silently filtered the `food_items` mutation out
(`route.ts` drops unparseable mutations by design so one bad row can't wedge the queue) → the client
saw no error for it and **deleted the outbox row** → the paired `food_logs` mutation failed
`foodLogRefsValid` (the item never reached the server) and **dead-lettered** → the adapter's
fully-built `food_items` push branch was unreachable dead code. Local-first reads still rendered the
food, which is why it was silent. Every new/scanned food logged since the `food_items` domain shipped
was server-absent with its log dead-lettered.

## Fix

- **Core (D-1):** added `'food_items'` to the envelope. To stop this drift class permanently, the
  enum is now built from one canonical `SYNCED_MUTATION_DOMAINS` array in `mutation-schema.ts`, and
  the local-store `PendingMutation['domain']` type (`lib/local-store/types.ts`) is now
  `SyncedMutationDomain` derived from the same array — the type and the wire enum can no longer
  disagree (the exact shape of D-1: the type already listed `food_items`, only the enum didn't).
- **Coverage (D-2):** `mutation-schema.test.ts` gained (a) a food_items-parses regression and a loop
  over every canonical domain, and (b) a **source-scan test** that greps `lib/`, `components/`, `app/`
  (excluding tests) for `domain: '<literal>'` and fails if any literal is absent from
  `SYNCED_MUTATION_DOMAINS`. `check-push-mutations.js` only greps `this.db`/`sql` and structurally
  cannot catch an envelope gap; this test can.
- **Recovery sweep:** new `requeueStrandedFoodItems(userId)` on the local store, called from
  `pushMutations` before draining. For each dead-lettered `food_logs` mutation whose `last_error` is
  the FK check, it looks up the referenced food item in the local `food_items` table, re-queues a
  `food_items` mutation **timestamped with the log's (older) `created_at`** so `getPendingMutations`
  (ordered by `created_at`) always drains the item ahead of the log it unblocks, then re-opens the log
  (fresh `created_at`, attempts reset). Idempotent (skips if a `food_items` mutation for that id is
  already queued; skips if the local item is gone) and one-shot (a healed log leaves the `failed` set).
- **D-5 (informational):** `food_items` `applyDelta` has no clobber gate — verified safe today (items
  are immutable client-side reference data); left as-is, noted for a future food-item *edit* feature.

## Verification

# oura-ble-lfhf-rem-signal — LF/HF frequency-domain HRV as an independent REM signal

**Branch:** `feat/oura-ble-lfhf-rem-signal` · **Oura-derivation serial track** (last remaining item) · **v1.168.0 (minor — affects REM%)**

## What shipped

An LF/HF autonomic-balance term added to the BLE sleep stager — a **frequency-domain** REM/deep
discriminator physiologically independent of the time-domain terms already there (RMSSD, HR spread,
breathing irregularity). HF (0.15–0.40 Hz) tracks parasympathetic tone, LF (0.04–0.15 Hz) a mixed
sympathetic band; their ratio rises in REM (sympathetic-leaning) and falls in deep NREM. Because it is
a different decomposition of the tachogram — not a re-slice of the correlated time-domain signals — it
can move REM where re-weighting them cannot. Density-gated: silent (null → neutral) on sparse-beat
epochs, so nights without dense beats are unaffected. **A heuristic lever, not an Oura-parity claim**
(the trained-model route remains item 4 Phase 2 / SleepNet).

## Implementation

- **`lib/health/tachogram.ts` (new):** extracted the shared "IBI → clean beat stream → even-grid
  resample" step out of `breathing-rate.ts` into `resampleTachogram(ibiMs, fs)` (One-Formula-One-Place).
  `breathing-rate.ts` re-points at it, behaviour byte-identical (its 4 tests still pass).
- **`lib/health/hrv-frequency.ts` (new, pure):** `lfhfFromIbi(ibiMs)` → `{ lfhf, lf, hf }`. Resamples at
  2 Hz, mean-detrends + Hann-windows, takes a self-contained radix-2 Cooley–Tukey FFT periodogram
  (no new dependency), integrates power over the LF/HF bands, returns the clipped ratio. Density-gated
  at ≥90 beats / ≥4 min; returns nulls on sparse/short input; never throws.
- **Stager (`lib/health/sleep-staging.ts`):** `lfhf?` on `SleepEpoch`, a `zLfhf` self-neutralising
  z-score (null → 0), and a `W_LFHF` (0.5) REM term entering the depth/REM scores with the same sign as
  the breathing term. Deep and wake rules untouched; it rides the existing per-bout Viterbi decode
  unchanged.
- **Epoch builder (`adapter.ts` `aggregateOuraRawSamples`):** computes `lfhf = lfhfFromIbi(b.ibi).lfhf`
  per epoch from the same binned IBI stream that already feeds `breathVar`.
- **Debug surface:** `lfhf` added to `SleepNightDebug.epochs` (`repository.ts`), the adapter dump, and
  the `/admin/oura-ble` "Sleep epochs (debug)" table, so `W_LFHF` is tunable against redecoded nights
  and the density-gating (null = too few beats) is visible.

## Verification

- **Automated:** `tachogram` (4) + `hrv-frequency` (4, incl. HF-band vs LF-band separation) +
  `breathing-rate` (4, byte-identical after refactor) + `sleep-staging` (25, incl. new lfhf-neutrality
  and REM-growth tests) + the rollup end-to-end passthrough. Full suite / `tsc` / lint / build green.

  available); judged on ribbon plausibility + REM% vs the ~23–28% Cloud baseline, same as the whole

  is the lever — but check the `beats` column first (null `lfhf` = the density wall, where no weight

# health-data-provenance — item 17 Chunk A (per-field precedence merge)

**Branch:** `feat/health-data-provenance` · **item 17 Chunk A** · **patch bump (data-integrity fix)**

## What shipped

Per-field provenance for the three multi-source health tables, replacing the blind
`COALESCE(EXCLUDED, existing)` last-writer-wins that let a lower-priority source silently overwrite a
higher-priority value (e.g. a Health Connect / Oura Cloud write clobbering a manually-logged weight).

## The design decision (owner-chosen)

The plan's recommended row-level `source` model has a real flaw for `body_metrics`, whose fields
legitimately come from different sources on the same day: one source-stamp per row would freeze a
field's legitimate single-source updates (log a manual weight → the ring's HRV or HC's steps stop
updating that date). The owner chose **per-field JSONB** provenance instead — correct without a
separate table or a per-read join.

## Implementation

- **Migration 120** — additive, idempotent `source_map JSONB` on `body_metrics` / `sleep_sessions` /
  `oura_daily` (nullable; a legacy row reads as "unknown" = lowest precedence, so any explicit source
  corrects it). Drizzle schema + no mapper changes needed (the column is internal write-state, read only
  by the merge SQL).
- **`lib/data/health-source.ts`** (One-Formula) — `HEALTH_SOURCES` + `sourceRank`
  (manual > oura_ble > oura_cloud > health_connect > null), plus the shared SQL builders `mergeSet`
  (per-column `CASE` gating overwrite on `source_map->>'<col>'`'s stored rank, with the incoming rank
  inlined as a constant) and `initialSourceMap` (the INSERT-path map of non-null fields → source). The
  three upsert helpers import these and never re-implement the rank.
- **The three upsert helpers** (`upsertBodyMetrics`, `upsertOuraSleep`, `upsertOuraDaily`) take a
  required `source: HealthSource`; each field merges against its own stored source (`rank(src) >= stored
  field rank` overwrites; equal rank = newer wins; strictly-lower fills nulls only). `source_map`
  re-stamps only the fields a write actually won (`jsonb_strip_nulls` preserves the rest).
- **Writer sweep** — the required param made the compiler the checklist: all ~22 call sites updated with
  their tier — `manual` (body-metadata, ai-chat weight, the `pushMutations` device write), `oura_ble`
  (BLE rollup body/sleep/wear), `oura_cloud` (Oura sync + all webhook handlers), `health_connect`
  (health-connect/ingest, sync-health).

## Verification

- **`lib/data/__tests__/health-source.test.ts`** — rank ordering, `initialSourceMap`, `mergeSet` shape.
- **`lib/data/postgres/__tests__/health-source-merge.test.ts`** (DB-backed, 4 cases across all 3 tables)
  — manual weight survives an HC write, HC fills the previously-null steps AND keeps updating steps
  afterward (the row-level bug would freeze it), oura_ble beats oura_cloud on a shared sleep field, a
  legacy null-`source_map` row is corrected by any explicit source.
- **Dev-server HTTP smoke** — `POST /api/body-metadata` (manual weight 84.2) then `POST /api/sync-health`
  (HC weight 80 + steps 7000, then steps 9500): weight stayed 84.2 (`source_map.weight_kg=manual`), steps
  went 7000 → 9500 (`health_connect`). End-to-end through the real routes.
- Full gate green: 1750 tests, `tsc`, lint 0 errors, `check-push-mutations`, `check-reconcile`, build.

## Scope / not done

- **Chunk B** (promote `sleep_sessions` to a real offline-first domain — local SQLite migration,
  device-gated) remains, its own PR. Chunk C (sync-health Zod) shipped in #639.
- `saveSleepSession`'s Health-Connect sleep path stays `onConflictDoNothing` — it already can't clobber

# cumulative-stress-wiring-plan — plan the ChronicStress rollup/surface follow-on

**Branch:** `docs/cumulative-stress-wiring-plan` · **docs-only planning PR (PR 1 of the plan-then-build

## What shipped

A planning doc for wiring the already-shipped, golden-verified `cumulative_stress_1_2_2` (ChronicStress)
library port (`lib/oura-models/cumulative-stress.ts`) into the rollup + a Health surface. The port has
been on `main` since the library PR but was explicitly **not wired** (no input assembly, no rollup step,
no surface); the port plan deferred wiring to a follow-on that had no plan. This is that plan.

## Why a plan, not a same-session build

`runCumulativeStress` takes 27 inputs and hard-gates on `min_days_required = 21` — each of 9 required
series needs ≥ 21 non-NaN days in the 31-day window or every output is NaN. Four of those series are
**per-night preprocessor-derived intermediates** (30-element history), so the wiring is multi-night-
stateful, and a real non-null score only appears against ≥ 21 nights of granular real ring data
(hypnogram/HRV/temp-skin) — unreachable in the sandbox (the dev seed has no such signals). A subtly-
wrong assembly produces a plausible-but-wrong score that can't be caught here. That is the CLAUDE.md
"plan now, build later" case. The model itself is not the risk (golden-verified); the input assembly is.

## What the plan pins down

- **Full input → source mapping** (§1): most history series come straight from `DailySummaryRow`
  (`computeDailySummaries`); a few need small derivations (`gotUps` from hypnogram awakenings,
  `highestTemperature` from `max(temp_skin)`, `temperatureDevBaseline`); cycle inputs are all-NaN for
  this (male) user and the model degrades gracefully.
- **Three real gaps** to resolve at build time (§2): the latest-night **30-sec hypnogram** (we store
  only a 5-min one), the **`hrv_quality_5min`** series (unclear it's emitted — most likely reason a
  wired score stays permanently NaN; a coverage-based quality proxy is the pragmatic fix), and the
  21-day cold-start (a learning-state, not a bug).
- **Intermediate-history strategy** (§3): recompute per-night intermediates **in-memory each rollup
  pass** (no migration, no stored counter to drift) via a thin `computeNightIntermediates` wrapper over
  the port's existing feature-engineering — chosen over adding stored columns.
- **Rollup step** (§4) mirroring the stress-resilience step exactly (own step, bounded window, COALESCE-
  only upsert of `chronic_stress_score`/`chronic_stress_contributors` — columns already exist from mig
  123, NaN → null), and a **Health card** (§5) paired with the resilience tile (inverted band polarity —
  higher stress = worse — + explicit learning state).
- **Verification** (§6): synthetic-full-data unit test proving the assembly yields a non-null score;
  rollup smoke proving it fails safe to null on sparse data; the real non-null score is owner/on-device-
  gated (Known-Issue posture, same as BDI).
- **Two shippable chunks** (§7): Chunk 1 server wiring (sandbox-buildable, no version bump), Chunk 2 the
  client card (user-visible, device-gated).

# accessory-intensity-goal-rpe — goal-aware, RPE-targeted accessory load

**Branch:** `feat/accessory-intensity-rpe` · **Lane 1 (workout, file-disjoint from Oura)** · **v1.170.0 (minor — user-visible prescription change)**

## What shipped

Owner-reported fix: accessories prescribed from one hardcoded light band (`ACCESSORY = 55–75% /
8–15 reps` for **every** goal) whose low end read "RPE 6 · Light" and never climbed. Accessories are
now (a) **goal-aware** (strength accessories heavier/lower-rep than hypertrophy) and (b) **prescribed

- **`pctForExpectedRpe(targetRpe, reps)` (`expected-rpe.ts`):** the exact algebraic inverse of the
  existing `expectedRpe` — same `repFactor` curve, so the derivation and the slider readout can never
  drift (One-Formula-One-Place). `maxReps = reps + (10 − targetRpe)`, `pct = 100 / repFactor(maxReps)`.
- **Goal-aware bands (`goal-ranges.ts`):** replaced the single `ACCESSORY` with per-goal
  `ACCESSORY_SPEC` (`{repMin, repMax, targetRpe}`, all ≥ RPE 7.5) + `accessoryTargetRpe(goal)`; the
  pct band is **derived** from the target RPE at the rep-band edges (target RPE is the single source
  of truth, no second hand-tuned %).
- **Prescribe route:** the accessory-clamp loop branches on role — accessories get
  `clamp(pctForExpectedRpe(accessoryTargetRpe(goal), reps), 40, 85)`; compounds keep the existing
  phase-relative clamp. Also fixed `intensityZoneForRole` to return an accessory-appropriate zone for
  accessories (it previously returned the *primary* zone, which would re-floor the override).
- **Base-style path (`workout-data` route):** when an AI-dynamic accessory is still on its base style
  (no AI prescription driving it yet — exactly the state that produced the owner's live 60% reading),
  each weighted set's pct is re-derived from the goal target RPE. Bodyweight/baseline/deload excluded.

## 2026-07-17 — Fix: deload override read yesterday's daytime-stress, not today's — v1.166.1

**Branch:** `claude/rest-deload-option-rkkaq7` · **PR:** #TBD · squash-merge

### Symptom (user report)
On a fresh morning (streak 1, good sleep, Oura readiness "no data", energy OK, no soreness) the
home "Recommended Today" card showed the amber **Deload / Rest / Full** prompt and the "why this
session" signals listed **"Deload recommended"** — despite the user feeling fine and having rested
the day before. Separately, the per-exercise AI prescription was timing out ("Couldn't generate your
AI prescription… showing your base program") — an **unrelated** LLM path, not the cause of the deload.

### Root cause
The daytime-stress deload override read the **wrong day**. In `adapter.ts` `getNextSession`
(ai_dynamic branch) the derived-data read spans `[yesterday, today]` and
`getOuraDailyDerived` returns rows **ASC-sorted by day**, so `derivedRows[0]` is **yesterday**.
The illness signal correctly uses `latestIllnessFromDerived(derivedRows)` (scans for the latest
row), but the stress signal used `derivedRows[0]?.stressHighMinutes` — feeding **yesterday's**
high-stress minutes into today's `computeDeloadStrength`, which trips `stressOverride`
(`≥ STRESS_HIGH_DAY_THRESHOLD_MIN`) → a "recommended"-strength deload on a day with a 1-day streak
and null readiness (both of which otherwise say "no deload").

Two 2026-07-16 plans collided: the daytime-stress plan used a `todayIso→todayIso` range (where
`derivedRows[0]` *is* today), while the illness plan widened the range start to yesterday so its
latest-row fallback worked. Merged, the wider range won but the stress read still hard-coded index 0.

### Fix
`lib/data/postgres/adapter.ts` — select today's row explicitly for the same-day stress signal:
`const todayDerived = derivedRows.find(r => r.day === todayIso) ?? null` and read
`todayDerived?.stressHighMinutes`. This mirrors the already-correct readiness route
(`app/api/readiness-score/route.ts` `find(r => r.day === todayIso)`). Illness keeps its
latest-available fallback (illness persists across days; daytime stress does not).

- `tsc --noEmit` clean; `pnpm lint` 0 errors (pre-existing warnings only); full suite green
  (1567 passed, 32 files skipped = DB-gated).

  `skipIf(!DATABASE_URL)` integration convention): seeds a minimal ai_dynamic program + two derived
  rows and asserts (a) yesterday=180 / today=0 → **no** deload, (b) today=180 → deload. Ran against
  the local dev Postgres: **passes with the fix, fails when reverted to `derivedRows[0]`** (confirmed
  by temporarily restoring the buggy line). This closes the gap the daytime-stress wiring journal
  called out — the ai_dynamic deload path was previously unreachable from the (manual) seed program.

  `charging_time` over the wall-clock span, and flags `sane=false` on garbage (pct out of [0,100],
  implausible charge duration).
- **`getOuraBatteryEvents(userId, from, to)`** (read-only repo method): windowed 0x61 read anchored via the
  ring clock, the exact analogue of `getOuraDaytimeSignals` (decodes from `body_hex` when `decoded` is null).
- **Admin probe**: `GET /api/oura-ble/battery-analytics?days=N` (requireAdmin + rate-limited) → aggregator
  JSON; `RingBatteryConsole` on `/admin/oura-ble` renders drain/charge/avg-charge lines + a decoder-sanity
  warning + a Cloud-chip cross-check reminder.

# backlog-dual-agent-run — Steps motion decoder TS port

**Branch:** `claude/backlog-dual-agent-run-vl4tvb` · **Serial track** (Oura model ports) · **PR:** steps-motion-decoder port · **library port only, no version bump**

## What shipped

A verbatim TorchScript→TypeScript port of Oura's `steps_motion_decoder_2_0_0` at
`lib/oura-models/steps-motion-decoder.ts` → `runStepsMotionDecoder(input)`. A 0-parameter
deterministic dequantizer: it takes the ring's compact 30-second motion frames (`[N][27]`
quantized columns) and reconstructs gait features, expanding each 30 s frame into three 10 s
sub-rows (`[3N][11]`) with interpolated timestamps. **Golden-verified** — both outputs
(timestamps + gait features) are **bit-exact** vs the captured `.pt`.

**Library port only** — not wired into the ring's motion-frame decode (`lib/oura-ble/decode.ts`)
or the step-counter pipeline. It's the decode the step-counter follow-on needs to be fed real
ring data; feeding it live BLE frames + the admin export console is the follow-on.

## Implementation

- **Dequantization** (`decodeColumn`) — per-column linear dequant: `(code / 2^bits) ×
  (high − low) + low`, with the vendored `decoder_base_settings` (low/high/bits/encode_zero) and
  `decoder_transform_settings` (log/sqrt transform applied to the bounds, inverse applied to the
  result). A truthy `encode_zero` reserves code 0 for "no value" (shift down one, clamp, restore
  the zeros via the `> 0` mask) — only `stride_frequency` uses it. The transform table covers
  `log_transform`/`log_itransform`/`sqrt`/`square`, identity otherwise (the `""` default).
- **Column → settings** (`baseKey`) — strips the `_1`/`_2`/`_3` window suffix to reach the base
  key, matching the `.pt`'s `get_decoder_settings`.
- **Reshape** — each frame → 3 sub-rows: the 3 shared columns (`sum_accel_mg_std`,
  `y/z_accel_std_ratio`) copy to all three; the 8 per-window gait features take the `_1`/`_2`/`_3`
  group for sub-rows 0/1/2. Timestamps interpolate at `t − 2δ`, `t − δ`, `t` where
  `δ = frameGap // 3`; a frame gap outside 25.5–34.5 s is treated as a nominal 30 s.
- **Constants** — added `data_columns` to the `StepsDecoderConstants` interface (already vendored
  in the constants JSON); consumed via `getStepsDecoderConstants()` (One-Constant-One-Source).

## Verification

- **Golden parity** (`lib/oura-models/__tests__/steps-motion-decoder.test.ts`, 3 tests): both
  outputs bit-exact (`< 1e-3`) over the full 768×11 output; the 3N expansion + ascending sub-row
  timestamps; the `encode_zero` zero-restoration on `stride_frequency`.
- **Repro oracle** (`scripts/oura-models/dump-steps-motion-decoder-intermediates.py`): the scripted

## Implementation

- **classify** (Preprocessor) — thresholds each bin into fully/borderline stressed/restored using
  `extreme_stress_threshold` (0.5) and `relaxed_threshold` (0.4), plus a finite mask.
- **segment** (Processor) — two `_collect_pass` sweeps (stressed type −1, restored type +1): slide a
  fixed 4-bin window; accept a position when its covered span is within `[min,max]_window_delta_ms`
  (55–65 min) and the window passes `_accept_window` (rule 1: no "other" bins, ≤1 NaN, ≥1 fully-typed
  bin, borderline-ok). Accepted (possibly overlapping) windows are stable insertion-sorted by start,
  then adjacent same-type windows with a gap ≤ `allowed_merge_gap_ms` (30 min) are merged
  (`end = max(end, cur_end)`).
- **forward** — `durations_min = (end − start)/60000 + bin_width_minutes`; counts + total minutes per
  type. The 568-… (here 340-line) Validator is reduced to a pragmatic gate returning the empty/zero
  result on invalid input (too few bins, mismatched/non-increasing timestamps, dsa out of `[−1,1]`),
  never throwing. Constants via `getAstdConstants()`.
