## Session 2026-07-21 — Fix the Oura BLE sleep-epoch debugger timing out ("upstream error")

Owner was diagnosing a bad sleep night (2026-07-21 showing a 5:53pm bedtime / 12h "asleep") and the per-epoch debugger failed — first "Failed to fetch", then `Unexpected token 'u', "upstream error" is not valid JSON`. "upstream error" is the Railway edge returning a plain-text body when the upstream request times out; the client then can't JSON.parse it.

**Root cause:** the debug dump POSTs `/api/oura-ble/samples/redecode?date=…`, which (a) re-decodes EVERY stored raw sample and (b) re-aggregates ALL history — passing `debugDate` forced `fullHistory=true` (adapter line ~4000). Both are unbounded and grow with weeks of accumulated BLE data, so the request outlives the gateway timeout.

**Fix (server-side, admin-tool only — no end-user surface, no version/changelog bump):** added a lightweight `?dump=1` path to the redecode route that skips `redecodeOuraRawSamples` and calls `aggregateOuraRawSamples(..., { dumpOnly: true })`; the new `dumpOnly` flag stops `debugDate` from forcing full history, keeping the 35-day rollup bound. A recent night's diagnostic still returns (new DB test asserts it); only >35-day-old dumps are unavailable, which the tuning workflow never needs. The heavy full "Redecode" button is unchanged. Verified: typecheck clean (bar the sandbox's missing native `onnxruntime-node`/capacitor modules, which fail identically on clean main), 5/5 staging-rollup DB tests incl. the new dumpOnly case, lint 0 errors, custom rule OK.

**Still open — the 07-21 row itself:** the debugger reports *no BLE night* for 07-21, and the owner confirmed Health Connect is disabled (so not Samsung) and Oura Cloud is frozen since the re-key. ## Session 2026-07-17 (continued) — Fix: stale-session-id strands the AI prescription; make identity strictly id-based (v1.166.0)

**Owner report (Railway HTTP log):** `GET /api/ai-periodization/session/005dd0e9-… → 404` while
`/api/workout-data → 200` — the AI prescription "couldn't generate" on the Lower session even after
the v1.165.2 rate-limit fix. Root cause is NOT quota; it's a stale session id.

**Diagnosis (3 parallel Explore agents):**
1. **Offline mirror goes stale & pull-to-sync can't fix it.** The on-device program mirror
   (`local_programs`/`program_sessions`/`session_exercises`) is written ONLY by `applyDelta`←`pullDelta`,
   and the delta only carries the program subtree while `programs.updatedAt > since`. Once `lastSyncAt`
   passes the edit, the program is never re-pulled (cursor is monotonic; `force` only skips the
   throttle, not the cursor). Same-device edits never write the mirror at all (`invalidateProgramStructure`
   clears TTL caches, not the mirror). → the mirror keeps pre-edit session ids indefinitely.
2. **Every AI route keys strictly on id and 404s (no self-heal, no name fallback), and the client
   swallows the 404** (`.catch(()=>{})`) → silent "couldn't generate". `/api/workout-data`, by
   contrast, had a legacy `find by id ?? by name ?? sessions[0]` fallback that *masked* the bug
   (exercises loaded by name while the AI half correctly failed) — and `sessions[0]` would silently
   serve the WRONG session.
3. **Exercise ids are re-minted on every edit** (editor never round-trips `ex.id`), orphaning the
   AI `baseline1rm` map (keyed by session_exercise_id) on every program tweak.

**Owner steer:** strict id-only — identity is the DB id, never the name (CLAUDE.md rule). So the fix
keeps ids correct rather than teaching routes to guess by name.

**Shipped (v1.166.0):**
- **`/api/workout-data`: id-only resolution.** Dropped the name + `sessions[0]` fallbacks; a stale id
  now returns `{ sessionNotFound: true }` instead of silently the wrong session. The 3 card-prefetch
  callers (session-select / workout-select / overview) now pass `sess.id`, not `sess.name` — so every
  session load is by id.
- **Refresh the on-device mirror on save.** `config-screen` forces `pullDelta(userId, true)` right
  after `/api/workout-templates` POST (while `lastSyncAt` is still behind the edit, so the delta
  carries the re-saved sessions); `ConfigScreen` now takes `userId` (threaded from `more-content`).
- **`pullDelta(userId, force, fullResync)`** — new `fullResync` re-pulls from epoch (since=0) to rebuild
  a stale mirror from server truth (applyDelta still gates on `sync_status='synced'`, so pending edits
  survive). Used by the client recovery below.
- **Client id-based recovery** (`workout-screen`): an AI-fetch 404 forces a full mirror re-sync (no name
  matching, guarded against loops); a `sessionNotFound` from workout-data forces the re-sync and shows a
  "This session was updated — reopen it" reselect screen (a dead id is never silently remapped).
- **Round-trip exercise ids** through the editor (`EditableExercise.id`, carried in `openEditProgram`
  and the save payload; `saveProgram` already honours `ex.id ?? uuid()`) — baseline 1RMs no longer wiped
  on edits.
- **Prescribe self-heal**: validates the session by id in the active program then `ensureSessionPeriodization`
  (previously a valid-but-stateless session 404'd on prescribe even though GET would heal it).

**Verification:** `tsc`/lint clean (my files), full suite **1654 passing**, `build` green. **NOT
device-verified** — this is core offline-sync + workout-screen + navigation behaviour on the canonical

## Session 2026-07-17 (continued) — Fix: the "preparing" poll was rate-limiting its own AI generation (v1.165.2)

**Owner report (on-device):** the new "Preparing your AI workout…" state (v1.156.0, #584) rendered
correctly for a Lower session, then fell to the timeout fallback ("Couldn't generate… showing base
program") — the AI generation genuinely failed. Screenshots confirmed both the preparing state and
the fallback render correctly on-device (so that half of #584 IS now device-verified).

**Root cause (self-inflicted):** `/api/workout-data` fires a fire-and-forget `/prescribe` (a Gemini
`generateObject`) whenever it sees the pending state (`consumed` + null). `cachedFetch` always
revalidates against the network, so the pre-workout screen's ~3s poll re-hit workout-data every
tick — turning **one** generation into a **burst of ~8 `/prescribe` → 8 Gemini calls in ~24s**, which
trips `gemini-3.1-flash-lite`'s per-minute rate limit and 502s them all (the route returns
`{error:'AI generation failed'}` and stores nothing → stays pending → timeout → base fallback). The
feature was causing the very failure it was meant to mask.

**Fix:** a poll must only *read* whether the in-flight generation landed, never re-trigger it.
- **`app/api/workout-data/route.ts`**: new `?poll=1` param; when set, skip the `aiPrescriptionPending`
  fire-and-forget `/prescribe` (the reeval-regenerate path is unreachable while pending — it needs a
  present prescription — so only the pending fire needed gating). Still returns `aiPrescriptionPending`.
- **`components/workout-screen.tsx`**: `fetchExercises({ poll })` adds `&poll=1`; the poll effect calls
  it with `poll:true` (read-only), while the initial load and "Refresh now"/refresh keep firing a
  fresh generation (the manual-retry path). Net: exactly ONE generation per screen-open + one per
  manual refresh, no burst. Bumped the poll window 24s→30s (`PRESCRIPTION_POLL_MAX` 8→10) now that a
  single call isn't competing with 7 others.

**Verification:** `tsc`/lint clean (my files), full suite **1652 passing**, `build` green.
`isAiPrescriptionPending` helper test unchanged/passing. **On-device still needed** to confirm the
generation now actually succeeds (the rate-limit was the suspected cause; can't reproduce a real
Gemini rate-limit in the sandbox) — Known-Issues row updated. JS/server-only, ships via Railway.

## Session 2026-07-17 (continued) — Hotfix: unbreak the debug-APK build (MainActivity.onDestroy visibility)

failing on `main` — `MainActivity.java:343` had `protected void onDestroy()`, which Java rejects

unregister) at `protected`. The debug APK could not compile from `main` since that merge, so an owner
rebuild would have failed. One-token fix: `protected` → `public` on the override (the sibling
`onCreate`/`onNewIntent` overrides stay `protected` — those base methods *are* protected). Native-only
(no JS/server), so the sandbox can't compile it (Gradle proxy-blocked per CLAUDE.md) — the Android CI
job is the verifier; the six JS/server required checks are unaffected. No version bump (unbreaks a
build; no behaviour change).
