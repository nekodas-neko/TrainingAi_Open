## 2026-07-27 — Bodyweight strength is measured in reps (v1.219.0, audit finding Q-12)

Owner decision: *"I would like the 1RM to be REPS in general without regard for weight. But I don't
know how to do that cleanly. Whatever way you think would be most consistent."*

### The defect

`estimateOneRm` prices a bodyweight set at `BW_REF + addedKg` with `BW_REF = 100` **fixed**
(`lib/1rm.ts`), so the stored value is a pure function of reps. Before that constant landed the same
code used the lifter's real weigh-in, which drifted 67.6–72.8 kg across the window. The history
therefore holds two incommensurable eras, and the seam is visible as a fake achievement:

**Pull-Up read 82.0 on 2026-06-28 and 114.5 on 2026-07-05 — +39.6% on equal-or-fewer reps per set.**
It was recorded as a real PR (`personal_records.Pull-Up` @ 2026-07-05, the changeover session), and
it feeds the prescription engine's 1RM-trend signal.

Underneath that sat the deeper problem the owner named: a bodyweight "1RM" in kilograms is a number
the lifter never moved. It is an internal index. Showing it is what let a change of constant read as
strength.

### Locating the boundary

All 13 bodyweight logs in the history were re-run through the real module at `bwRef = 100`:

| | 2026-06-11 → 06-29 (6 rows) | 2026-07-05 → 07-26 (7 rows) |
|---|---|---|
| reproduces stored value at `bwRef = 100` | **none** | **all 7, exactly** |

That is decisive, and it is why the fix could be written as a value table rather than a guess.

### What shipped

**1. One place that answers "what unit is this exercise's strength in?"** — `displayOneRm`,
`displayOneRmDelta`, `displayOneRmSeries`, `oneRmUnit`, `oneRmLabel`, `isBodyweightType` in
`lib/1rm.ts`. Bodyweight inverts through the existing `repMaxFromOneRm` (at the added load, so a
weighted pull-up isn't read back at bare bodyweight); weighted passes through as kg. The rep-max
display already existed in `exercise-summary-screen.tsx` — this extracts it instead of adding a
second copy, and a bodyweight delta is now a whole number of reps, so sub-rep drift reports `0`
rather than a meaningless fractional kg.

**2. Migration 148 rebases the six pre-changeover rows.** No rep count and no logged weight is
touched — only the derived estimate, and only where it still holds exactly the value the old constant
produced (so it is idempotent, and inert on a row edited since):

| | reps | stored | rebased | rep max |
|---|---|---|---|---|
| Pull-Up 06-11 | 5 | 78.75 | 114.50 | 5 |
| Pull-Up 06-17 | 4,4,3,3 | 80.50 | 109.75 | 3 |
| Pull-Up 06-21 | 7 | 82.75 | **118.00** | **6** |
| Pull-Up 06-28 | 5,4,4,5 | 82.00 | 113.00 | 4 |
| HLR 06-23 | 11 | 93.75 | **128.00** | **8** |
| HLR 06-29 | 10,10,10 | 104.75 | 124.00 | 7 |

The +40% rally disappears: Pull-Up now reads 5 → 3 → 6 → 4 → 5 → 5 → 5 → 4 reps across the whole
history, which is the truth — the lifter has been at 5–6 reps since June.

**The formula is not restated in SQL.** The replacement values were generated by calling
`estimateOneRm` and are pinned by a test that recomputes all six; if the formula ever changes, that
test fails and the migration's constants are known stale.

**3. Both phantom PRs re-derived** from the corrected logs, by pure aggregation over the column the
statement above just fixed: Pull-Up 114.5 (2026-07-05) → **118.0 (2026-06-21)**, Hanging Leg Raise
123.25 (2026-07-07) → **128.0 (2026-06-23)**. The gate mirrors `reconcilePersonalRecord` exactly,
including NULL `phase_type` counting as "not deload".

**4. Every display surface with the type available now renders reps**: the overview 1RM/working
columns, `strength-progress.ts` (the split-brain spot — its "1RM" mode had no bodyweight branch while
its "Sets" mode did) and its card's delta, the strength-trend card end-to-end, the exercise-history
sheet, the active-workout 1RM chip and trend sparkline, the pre-workout line, the exercise-stats
sheet, and the summary screen's sparkline (which was still kg-labelled directly under the branched
rep-max card). `/api/exercise-history` and `/api/strength-trend` now return `exerciseType`; they
previously could not branch at all.

### Verification

Full CI-equivalent suite **2,334 passing** (21 new), typecheck and lint clean. Migration 148 applied
through the real runner against local Postgres: a seeded PR pointing at the latest log moved to the
older, stronger one (114.5 → 118.0). `pnpm dev` exercised both changed routes — `exercise-history`
returns `bodyweight` for Pull-Up and `weighted` for Barbell Bench Press; `strength-trend` re-types
correctly when an exercise's library type is flipped.

The cross-user case is tested and was a real catch: the PR re-derive was first written as
`DISTINCT ON (exercise_name)`, which would have stamped one account's best onto **every** user's
record for that movement. It is partitioned by `user_id` and there is a test that fails without it.

**Not exercised — on-device.** No native path is touched, but none of the reworked cards have been
seen on the S25.

### Two findings filed rather than fixed

- **Q-19** — ten AI prompt/context builders still inject the raw kg number, and `ai-chat` instructs
  the model to *"Quote them exactly"*, so a Pull-Up reads back to the user as "118 kg". Same helpers
  fix it; the work is threading `exerciseType` into builders that don't fetch it.
- **Q-20** — the local store has no `exercise_library` table, so `program-assembler.ts` hardcodes
  `exerciseType: 'weighted'` and every offline read mistypes bodyweight movements. Pre-existing, and
  APK-only, so invisible to `pnpm dev`.

### Consequences worth knowing

- **Q-13 (bodyweight volume = 0) is now the open half.** Strength is settled as reps; what a
  bodyweight set is worth in *volume* is still undecided.
- **Q-5 is unblocked and narrowed** — the two bodyweight PRs are already corrected, so it is now only
  about the five weighted rows and the unguarded seed route.
- `gainPct` on the strength-trend card is still a percentage of the `BW_REF`-relative value for
  bodyweight. Post-migration the series shares one basis so the ratio is at least well-defined, but
  it is not a percentage of anything physical. Left alone deliberately; revisit with Q-13.
