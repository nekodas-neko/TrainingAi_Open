## 2026-09-07 — Production runs Node 22, so CI was the outlier (LA-60)

**Branch:** `fix/ci-node-22` · **Lane A**

### The question the entry could not answer, answered

LA-60 offered two fixes — pin the sandbox back to Node 20, or raise CI to 22 — and said the choice
could not be made "without checking [what Railway runs] first", because nothing in the repo says.
`nixpacks.toml` pins no version, there is no `.nvmrc`, and `package.json` had no `engines`. No
endpoint reports the runtime.

**It was measured, for free, from production stack traces already in `error_events`.** Node prints
its internal frames with file and line, and those line numbers are version-specific. Three frames
from a live production error, against the sandbox's Node **22.22.2** sources:

| production frame | Node 22.22.2 source at that line |
|---|---|
| `abortIncoming (node:_http_server:838:17)` | `req.destroy(new ConnResetException('aborted'));` |
| `socketOnClose (node:_http_server:832:3)` | `abortIncoming(state.incoming);` |
| `Socket.emit (node:events:531:35)` | `const result = listeners[i].apply(this, args);` |

Three for three, and the statement at each line matches the frame's own function name — so this is
not a coincidence of numbering. **Production is Node 22.** The sandbox is Node 22. `android.yml` and
`android-emulator.yml` were already on 22. Only `ci.yml`'s five jobs were on 20 — testing against a
runtime nothing ships on, which is exactly backwards from what CI is for.

### What shipped

- **`ci.yml`: five `node-version: '20'` → `'22'`** (Lint, Tests, Build, Migration Check, E2E).
- **`package.json`: `"engines": { "node": "22.x" }`.** This pins what nixpacks picks rather than
  changing it — production already builds 22 — and closes the gap where Railway could move to a new
  major with no commit anywhere in the repo.
- **`scripts/check-node-version-agreement.js`**, in Custom Rules (now **70** steps): fails when any
  workflow's `node-version` major differs from `engines.node`, or when `engines.node` is missing.

The guard is deliberately a **version** agreement, not a banned-API list. The entry makes that point
and it is right: a list of Node-22 APIs goes stale the moment Node 23 ships, whereas the thing that
must be true is that the runtimes match.

### Verification

- `pnpm check:rules` — **Ran 70 of 70**, the new step included and counted from the YAML.
- **Mutation-checked both ways**: drifting one workflow back to `'20'` exits 1 naming the file and
  line; deleting `engines.node` exits 1 with the nixpacks reason. Clean tree exits 0.
- `tsc --noEmit` clean, `check-test-typecheck` at baseline, `pnpm build` exit 0, full suite green —
  all on Node 22.22.2, which is now what CI runs too, so for the first time that is a like-for-like
  result rather than a hopeful one.

**Not exercised: the deploy.** I verified what Railway's Node *is*, not that nixpacks reads
`engines.node` here — if it ignores the field the line is inert rather than wrong, and either way it
matches what production already builds. The first merge after this is the thing that proves it, and
a failed nixpacks build leaves the previous deployment serving rather than breaking production.
Nothing else in this diff reaches the runtime.

No version bump: CI configuration only.
