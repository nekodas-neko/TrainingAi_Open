## 2026-07-27 — D2 Tasks 2 + 3: native `oura_raw.db`, local-commit cursor gate, WebView bridge

**Branch:** `feat/d2-native-raw-store` · native (Kotlin) + one TS interface · no version bump
(nothing user-visible changed)

### The problem

The Oura history cursor lived in SharedPreferences. The frames it pointed past lived on a server,
across a network. Two stores that can die independently fail in exactly one direction: the cursor
survives, the data doesn't — and because the ring's history buffer only moves forward, the drained
span is then gone permanently. Every other durability fix in this pipeline (I2, I6, I18) has been a
patch on the same underlying shape.

### What shipped

- **`android/app/src/main/java/com/trainingai/app/oura/OuraRawDb.kt`** — the device-owned archival
  store. `oura_raw.db` with `journal_mode=WAL` and `synchronous=FULL` set **after** open (never
  inside a transaction — the rule that killed the local SQLite store twice before), holding `raw`
  (`ring_ts`/`tag`/`event_name`/`body_hex`/`measured_at`/`rolled_up`/`synced`, `UNIQUE(ring_ts,
  tag, body_hex)`) and `sync_state` (`k='history_cursor_ds'`). `insertBatchAndAdvance` writes the
  batch **and** the cursor inside one transaction, returning true only after `endTransaction()`.
  The cursor is monotonic via an explicit read-then-write rather than an UPSERT: `ON CONFLICT DO
  UPDATE` needs SQLite 3.24 and minSdk 26 ships 3.19, so the upsert form would throw on an old
  device instead of advancing.
- **`OuraRingService.postDrainBatch` rewired** — gates on the local commit, not the POST. The POST
  became `postFramesBestEffort`, which marks its own batch's rows `synced=1` on a 2xx and gates
  nothing. It fires **even when the local commit failed**: Railway is the off-device copy and it
  matters most precisely then.
- **Cursor reconcile** — `oura_raw.db.sync_state` is now authoritative, SharedPreferences a mirror.
  On drain start the two are reconciled to their **minimum**; they can only disagree because one
  store died independently, and only re-draining is safe.
- **Failure surfaces** — `SQLITE_FULL` holds the cursor and raises `lowDisk`; a raw DB that cannot
  be opened at all degrades to the old server-2xx contract rather than wedging the drain forever.
  Both are reported in the plugin status (`lowDisk`, `rawStoreOpen`) and documented as ops-doc rows
  I21/I22.
- **`OuraBlePlugin.kt` bridge (Task 3)** — `getUnrolledRaw`, `markRolledUp`, `markSynced`,
  `pruneRaw`, `rawStats`, plus the matching TS interface in `lib/oura-ble/plugin.ts`. The WebView
  never opens the file: one SQLite library per WAL, no two-writer `SQLITE_BUSY`.

### Two deviations from the written spec, both deliberate

- **`markSyncedUpTo(maxDs)` → `markSyncedRange(minDs, maxDs)`.** Batches POST independently, so
  "everything up to maxDs" lets a later success vouch for an earlier batch that failed — marking
  never-uploaded rows prunable. `body_hex` is the only thing a future decoder fix can be re-run
  against, so it must never be deleted on someone else's word.
- **`getUnrolledRaw` never splits a `ring_ts` across calls** (the returned batch can slightly
  exceed `limit`). Rows are marked consumed *by `ring_ts`*, so a split would let the caller mark
  rows it never saw — a silent skip.

### Verification

The sandbox blocker recorded in the handoff was wrong: `dl.google.com` is reachable through the
proxy, so the Android SDK installs and `/opt/gradle` already matches the wrapper's 8.14.3. Future
native sessions should install the SDK rather than assume it's impossible.

- Kotlin compiles (`gradle :app:compileDebugKotlin --rerun-tasks`); debug APK assembles.
- 23 JVM protocol tests pass, including 3 new ones pinning the native frame split (`ring_ts` /
  `tag` / `body_hex`) to vectors generated by running the TS authority `historyEventFromHex` over
  the same hex — so a native row and a server row for one frame are byte-identical and dedup
  against each other.
- `lib/oura-ble/__tests__/event-names-kotlin-parity.test.ts` parses the Kotlin `EVENT_NAMES` map
  out of the source and fails CI if it drifts from `decode.ts` (confirmed it fails on an
  intentional one-character mutation). The map had to be duplicated — Kotlin names a row before any
  JS runs — so the drift guard is the price of that.
- Every SQL statement in `OuraRawDb` was replayed against a real SQLite engine (`node:sqlite`):
  single-transaction insert+cursor, **kill-mid-drain rollback** (neither rows nor cursor survive),
  dedup on re-drain, same-`ring_ts`-different-tag is not a dupe, cursor monotonicity, the `min()`
  reconcile, the no-split-`ring_ts` read, prune eligibility, and the `markSyncedRange` scoping.
- `tsc --noEmit`, `eslint`, `check-push-mutations`, `check-reconcile` all clean.

### Failure surfaces NOT exercised

Everything involving the ring or the phone. No BLE radio, no Android SQLite at runtime, no drain,
no real disk-full. The SQL semantics are proven; the Android bindings around them are not. The
gate is the owner's S25 run: ops-doc §4 step 3b (drain, per-event counts vs delivered, cursor
advanced) and the kill-mid-drain test. Until then this is implemented-and-compiled, not verified —
see the `projectOverview.md` Known Issues row.

### Known-by-design gap

`measured_at` is written NULL until D2 Task 4's clock anchor exists — ring deciseconds are a
counter from the ring's own epoch, not wall-clock, and a guessed timestamp is worse than an absent
one. Consequence: `pruneRaw` has nothing eligible yet, so the raw table only grows until Task 4
lands. Tasks 4+ are blocked on the device verification above.
