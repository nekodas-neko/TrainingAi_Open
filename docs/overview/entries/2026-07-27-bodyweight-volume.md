## 2026-07-27 — Bodyweight sets are worth something now (v1.227.0, audit finding Q-13)

`lib/workout/log-exercise.ts` priced a bodyweight set at `BW_REF + added` for the 1RM **and** for the
intensity percentage, but computed volume from the **raw** logged weight — 0 kg for an unloaded
bodyweight set, three lines apart in the same function. So the same rows simultaneously read as
82–88% intensity and zero work done.

208 real reps (19 Pull-Up sets, 13 Hanging Leg Raise sets) were absent from lifetime volume, weekly
volume, `computeVolumeAcwr` — which gates the early-deload recommendation — and the prescription
engine's own volume budget.

### What shipped

Owner decision: price a bodyweight rep at the lifter's **real body weight × a per-exercise
fraction**. New `lib/workout/bodyweight-load.ts` holds the fractions; the live write path looks up
the most recent weigh-in at or before the session.

Deliberately **not** `BW_REF`. That constant exists so the 1RM estimate stops tracking weigh-ins
(finding Q-12), and reusing it here would put ~100 kg on every rep:

| approach | added to lifetime volume |
|---|---|
| real body weight × fraction (**shipped**) | **8,856 kg** (~3.5% of 251,516 kg) |
| the internal `BW_REF` constant | 20,800 kg — pull-ups would become a top-3 volume contributor |

Fractions come from standard segmental mass fractions (Dempster/Winter): each leg ≈ 16.1% of body
mass, head ≈ 8.1%, trunk ≈ 49.7%. Pull-Up suspends all of you (1.00); Hanging Leg Raise raises both
legs (0.32). These are population averages, not measurements of this lifter — good enough to make
volume comparable across exercises, and wrong in the same direction for everyone.

**Isometrics are deliberately unpriced.** Plank "reps" are seconds, so reps × load is not work in the
same currency as every other row; pricing them would corrupt the totals rather than complete them.
They stay at zero volume with the reason written down.

**Migration 152** backfills the 13 historical logs, values generated by the real module (never
restated in SQL) using each session's own nearest weigh-in. Guarded to only ever fill a zero, so a
re-run is a no-op and a row edited since is left alone.

### A bug I introduced and caught on the dev server

The first implementation read `[...metrics].reverse().find(...)`. `listBodyMetrics` already returns
**newest-first** (`ORDER BY date DESC`), so reversing it made `find()` take the **oldest** weigh-in in
the 90-day window. A logged Pull-Up came back at 1,473.30 kg instead of 1,485.00 — 81.85 kg/rep, which
turned out to be the weigh-in from **2026-07-14**, two weeks stale.

It produced a *plausible* number, which is exactly why it would have survived a glance. Doing the
arithmetic on the result rather than accepting it is what caught it. Two regression tests now pin the
ordering, one of them asserting specifically that the stale value is **not** used.

The migration's values were unaffected — those were generated by a SQL query that took
`ORDER BY bm.date DESC LIMIT 1` explicitly.

### Verification

Full CI-equivalent suite green, typecheck, lint and both custom-rule checks clean. 12 tests on the
factor module (including one pinning it against migration 152's literals, so the two cannot drift),
3 DB-backed tests on the migration, 4 on the live write path.

**End-to-end on `pnpm dev`** against a local weigh-in of 82.5 kg:

| logged | bar weight stored | volume | intensity |
|---|---|---|---|
| Pull-Up 3×6 @ 0 kg | `0x6,0x6,0x6` | **1,485.00** | 87.3% |
| Barbell Bench Press 3×5 @ 80 kg | `80x5,80x5,80x5` | 1,200.00 | 87.2% |

`set_logs.weight_kg` correctly still records what was on the **bar**; only volume changed.

**Not exercised — on-device.** The write path is shared with `pushMutations` (per the Canonical
Runtime rule) so the APK uses the same function, but no on-device log was made.

### An invariant this deliberately breaks

Before this, `exercise_logs.volume` always equalled Σ(`set_logs.weight_kg` × reps) — the first
production audit verified that on all 288 logs. These 13 rows no longer satisfy it, because
`set_logs.weight_kg` records the **bar** (0 kg) while volume records work **done**. Any future check
of that invariant must exempt bodyweight exercises rather than "correcting" these back to zero. It is
called out in the migration header for exactly that reason.

`user_stats` derives its totals from these rows, so lifetime volume and ACWR pick the change up on
their next read — no stored counter to migrate.
