## 2026-09-02 — BF-107 has no engine half: the calories already reach the client, both ways (re-laned A → B)

**Branch:** `claude/la-bf107` · **Lane:** A, handing the entry to B · **Docs only** — no code changed,
because there was no Lane A code to change.

### What the entry claimed

> **Lane:** A — the value has to reach the client before Lane B can render it; the tile itself is
> trivial once it does.

and recommended *"return the derived kcal from the save"*. That single claim is what made this Lane
A. It is false, and the recommendation is already implemented.

### What the code does

**Web fallback — the value is in the response already.** `app/api/activity-logs/route.ts:45` returns
`{ activityLog }` from `saveActivityLog`, whose signature is `Promise<ActivityLog>` and which sets
`caloriesBurned = data.caloriesBurned ?? await this.deriveActivityKcal(...)` (`adapter.ts:2121`).
`walk-summary.tsx` throws that response away: `if (!res.ok) throw new Error()`, then `setSaved(true)`.

**Device — the pull already carries it.** `sync-engine.ts:337` maps
`caloriesBurned: (r.caloriesBurned as number) ?? null` into a real local column, written by
`upsertActivityLog` (`sqlite-backend.ts:1678/1690`). Nothing needs adding for it to land.

**The one genuine nuance, and it is not Lane A either.** The outbox push does not apply the server's
row — the `activity_logs` branch (`sync-engine.ts:968-980`) only flips the existing local row to
`synced`, deliberately. So on device the number arrives on the **next pull** rather than at first
paint. That is precisely the `—`-then-fill behaviour the entry already asks for, and a component can
get it by reading the local row.

So the whole gap is `walk-summary.tsx:239-241`: three hardcoded tiles, no read-back of the saved row.
`components/**` is Lane B by the path rule.

### Why this is not another LA-47

LA-47 was genuinely one change across two lanes because the halves **do not compile apart** — a new
`CoachWidgetSchema` member is a type error until the registry handles it. Nothing here has that
property: adding a tile that reads a field which already exists breaks no build. With no
compile-coupling and no engine work, a cross-lane PR would be crossing lanes for no reason.

### The sibling, checked rather than assumed

The entry asks whether `done-activity-screen.tsx` shows calories today. **It does not** — it passes
`caloriesBurned: null` at lines 210 and 242 and renders no energy tile. Same one-tile change, same
PR, recorded on the entry so Lane B does not have to re-derive it.

### The near-miss worth recording

`RECONCILE_COLUMNS` looked like the mechanism for "server-derived fields flowing back" and is not —
it is local SQLite *schema* reconciliation for columns whose `ALTER` may half-apply. Reaching for it
would have produced a confident, wrong fix in a file that had nothing to do with the problem. The
flow-back is the ordinary pull mapping.

### What was not done

No code, no tests, no device check — there is nothing here to exercise. The tile itself, its `—`
state and the offline case (where a dash rather than a `0` is the honest render, since a zero is a
claim) are all Lane B's, and the entry keeps those notes intact.
