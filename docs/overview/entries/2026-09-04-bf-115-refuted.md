# 2026-09-04 — the sleep fix that would have invented an 11.5-hour night (BF-115, refuted)

**Branch:** `fix/bf-115-sleep-detail` · Lane B · **docs only. No code shipped, deliberately.**

BF-115 arrived with a root-cause note from Lane A that ended: *"The fix, and it is small: run the
local rows through the same `mergeByDate` before setting state… no Lane A change is needed… the only
edit is in `app/health/health-content.tsx`."* Re-laned to B on that basis.

Reading it to the end before typing it, the edit does not fix the reported symptom, and it fabricates
a number.

## Three steps, each checkable

**It cannot restore the hypnogram, because the local rows have no timestamps to restore.** The render
condition is `r.sleepPhase5Min && r.sleepStart && r.sleepEnd`. **`LocalSleepSession` has no
`sleepStart`, no `sleepEnd`, no `awakHours`** — and that is confirmed at the storage level rather than
in the type alone: `sqlite-backend.ts`'s `sleep_sessions` insert names `manual_sleep_start` and
nothing else of the kind, and that column is Q-519's user-remembered bedtime, which its own comment
says is *"never read by anything deriving a window"*. A merge cannot invent the two fields the
condition tests.

**The clustering the fix leans on is disabled for exactly these rows.** `primaryCluster` opens with
`const timed = list.filter(r => r.sleepStart && r.sleepEnd)` and returns the list untouched when
`timed.length <= 1`; line 57 keeps untimed rows explicitly. For local rows `timed` is empty, so the
nap-dropping it is credited with never runs.

**And what is left is an additive merge.** All three rows carry an `ouraId` (`ble:…`), so the
mixed-source branch is skipped and they hit the same-source path, which **sums** the stage fields. On
the owner's own date: **7.67 + 2.00 + 1.83 = 11.5 hours**, deep 1.75 h, carrying whichever phase
string `list[0]` held. A fabricated eleven-and-a-half-hour night is worse than a missing chart, and it
would have been worse in the quiet way — a plausible number on a screen, not an empty section anyone
would report.

The additive merge is not the villain. It is built for Samsung midnight *splits* — contiguous
fragments of one night — and `primaryCluster` is what guarantees it only sees those. Untimed rows
disable that guarantee and hand two naps to a summer.

## What this changes

BF-115 is re-laned **back to A**. The real requirement is `sleepStart`/`sleepEnd` (and `awakHours`)
in the local table, which is a local SQLite version bump plus RECONCILE, and CLAUDE.md puts local
SQLite versions with Lane A alone.

**Everything else the 2026-09-03 investigation established still stands and is good work:** the three
rows are a night and two naps rather than duplicates, storage is correct, `/api/sleep-sessions` merges
correctly, and the defect is that `health-content.tsx:299` seeds raw local rows past that merge
through an `as unknown as SleepRow[]` double cast. That cast remains the enabling mistake — it is what
let two types differing by three load-bearing fields be treated as one. The note's error was in the
last paragraph, not the diagnosis.

A Lane B mitigation does exist — stop seeding sleep rows from the local store on this surface, so the
sheet reads the merged server payload — but it trades a wrong stages section offline for a blank one,
which the instant-paint rule normally calls the worse outcome. That is a judgement call for whoever
owns the schema change, not something to slip in alongside it, so it is recorded on the entry rather
than taken.

One line is added to the device verification: **no date may report a duration larger than its longest
single session.** That is the assertion that would have caught this fix.

## Not exercised

No code changed, so there is nothing to exercise. The refutation is read from source — the local
schema, `primaryCluster`, and the merge branch — and from the production rows the earlier
investigation recorded. It has not been observed on a device, and does not need to be: the claim is
that a proposed edit is unsafe, and the three steps above are each checkable in the files named.
