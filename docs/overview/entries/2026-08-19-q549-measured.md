# 2026-08-19 — Q-549's two candidates measured and falsified before implementing

**Branch:** `docs/q549-measured` · **Lane:** Implementation A

## Why this is a docs PR and not a config change

Q-549 says Postgres holds **0.79 GB to serve 171 MB at 0.002 vCPU** — *"$7.87/month of memory for a
database that does essentially no work"* — and names two candidates: `shared_buffers` sized for the
container, and up to 12 backend processes each carrying their own memory.

Both are readable from production through the existing read-only endpoint, so they were read rather
than assumed. Neither survives.

| reading | value | consequence |
|---|---|---|
| `shared_buffers` | **128 MB** (16384 × 8 kB) | the Postgres **default** — not "sized for the container". **Candidate 1 falsified.** |
| cache hit ratio | **99.866%** — 10,063,661 buffer hits vs 13,485 disk reads | 128 MB is comfortably sufficient. Shrinking it is the wrong direction; growing it buys nothing. |
| live backends on `railway` | **3** (2 app, 1 `claude_readonly` — this session's own) | not the "up to 12". **Candidate 2 is not the current driver.** |
| `work_mem` | 4 MB | per-backend private memory is single-digit MB at this backend count |
| `max_connections` | **500** | against a ceiling of ~12 (`max: 10` + `PG_POOL_MAX=2`) |
| database size | **188 MB** | up from the entry's 171 MB, consistent with the ~0.4 MB/day trend |
| version | PostgreSQL **18.6** | |

## What is actually left

**One over-provision is visible from inside: `max_connections = 500`.** Postgres pre-allocates
per-connection shared structures at startup, so that cost is paid at boot whether or not the
connections are used. Whether Railway's managed Postgres lets it be changed is an owner/console
question, not a code one.

**And the premise itself may not hold.** Most of a Postgres container's RSS on a ~190 MB database is
`shared_buffers` plus OS page cache — **reclaimable, not a leak**. The entry's own note that memory
*"grows as caches warm"* describes exactly that. 0.79 GB may be near the floor for this container
rather than waste, in which case there is nothing to reclaim and the line item stays.

## Stated plainly: what this could not settle

**Container RSS attribution.** Railway's metric is the authority and a sandbox cannot see it —
nothing inside Postgres reports what the container is charged for. The 0.79 GB figure is from
2026-08-18, taken **immediately after a volume incident and restart**, which the entry itself flags as
the wrong moment to measure. Before anyone spends a session here, the owner should confirm the
warmed steady state is still real.

That is why this ships as an annotation rather than a change: the next implementer would otherwise
start with `shared_buffers`, find a sane default and a 99.87% hit ratio, and have to re-derive all of
this before concluding there is nothing to do there.

**Not exercised:** no configuration was changed, nothing was restarted, and no write touched
production — read-only queries through `claude_ro` only.
