# 2026-08-23 — Q-555's open question, answered from the call sites (not the router)

**Branch:** `docs/q555-diagnosis` · **Lane A** · docs-only · **hands Q-555 to Lane B**

Q-555: offline, a tab tap does nothing until the service worker claims the page. Its measurements
were good — `controller: true` navigates and paints ~101% of cached content, `controller: false`
leaves the URL unchanged with no offline page and no feedback at all. What it lacked was a cause:

> *"Not diagnosed: whether the no-op is Next's router aborting a failed RSC fetch or the click handler
> swallowing it. That needs the router's internals, not another probe."*

**It is both, the click handler is what makes it silent, and it needed neither the router's internals
nor a probe — it needed reading the call sites.**

## The chain

1. **`components/shell/tab-loading.tsx`** is the `loading.tsx` fallback for every tab route, so it is
   what is on screen during a first-ever load — **precisely the uncontrolled window**. It renders
   `<BottomNav />` **with no `onTabChange`**.
2. Inside `TabShell`, `BottomNav` gets `onTabChange={show}`, so a tap is pure in-app state and never
   routes at all. That is why the controlled case works, and it is not the same code path.
3. `handleNavClick` (`bottom-nav.tsx:77`) calls **`e.preventDefault()` unconditionally**, then
   `navigateWithTransition` → `router.push(href)`.

The `<Link>`'s native navigation is therefore suppressed on **every** tap, leaving `router.push` as
the only path — and its RSC fetch cannot be served offline with no worker in control.

**The `preventDefault()` is what removes the fallback.** Without it a failed navigation is a real
browser navigation, and the browser shows *something*: its own offline error, or the precached
`/offline` page once the worker controls. With it, the failure has nowhere to surface.

## Measured, code fact, inferred — kept apart

| | |
|---|---|
| **Measured** (original review) | `controller: false` → tap does nothing, no feedback |
| **Code fact** (verifiable now) | the three points above |
| **Inferred** | that the App Router aborts the failed RSC fetch without surfacing anything |

The inference is standard App Router behaviour and fits the measurement, but it is an inference and
labelled as one. Confirming it is a Playwright run — `context.setOffline(true)`, worker unregistered,
watch the RSC request fail — not another round of reasoning.

## No Lane A fix is hiding in the service worker

Worth ruling out, because the entry's title points at the worker. `public/sw-template.js` already
calls `self.skipWaiting()` on install and `self.clients.claim()` on activate, so it takes control as
early as it can. The uncontrolled window is inherent to a first-ever load: the worker registers
*during* that navigation. **There is nothing to make faster there** — the fix is in the click handler,
which is `components/**` and so Lane B's.

## What was handed over

Q-555 now carries the diagnosis, an explicit `Lane: B`, and a fix *shape* rather than a prescription:
stop suppressing the native navigation where there is no `onTabChange` to run — outside the shell the
`preventDefault()` buys nothing — or keep it and give the failed `router.push` a visible outcome. The
first is smaller and restores a browser behaviour the app currently discards.

Before this, the entry had no lane field at all, so it sat in **both** lanes' queues as the top
unstartable item.
