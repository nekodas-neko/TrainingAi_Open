**The problem:** the existing orchestrator (`components/workout-screen.tsx`) tracks `store.currentIdx`/`store.currentSet` and logs an entire exercise's sets into one flat accumulator buffer (`store.setWeights`/`lapTimes`/etc.), snapshotted and POSTed as a single batch only once `currentSet >= sets` — i.e. only when that exercise finishes. This is incompatible with true interleaving: alternating to a superset partner mid-exercise would overwrite the first exercise's in-progress buffer before it's POSTed.

**Shipped:** `lib/stores/workout-store.ts` gained per-exercise WIP buffers — `stashExercise(idx)` snapshots the currently-loaded flat fields into `exerciseBuffers[idx]`, `restoreExercise(idx)` pulls a stash back (returns `false` if none exists, telling the caller to init fresh). `components/workout-screen.tsx` computes the session's full set-by-set order once via `buildSetSequence` (from sub-PR 1, `lib/workout/superset-order.ts`) in a `sequence` useMemo. A new `switchToExercise()` callback (stash current, restore-or-init target) fires from `handleLogCurrentSet` whenever `nextStep(sequence, ...)` says the next step belongs to a different exercise than the one just logged and this exercise isn't yet on its own last set. `advance()` (fired from the exercise-summary "Continue" button and the Skip button) gained the same restore-or-fresh-init check for the same reason — a superset partner may already be mid-way when this exercise's own summary is dismissed. Both `handleLogCurrentSet`/`handleCompleteSet` (the actual POST + PR-check logic) run **completely unchanged** for both the grouped and ungrouped case — only the "what's the next exercise" decision changed.

The per-set-weight-init effect (recomputes target weights whenever `currentIdx` changes) is skipped exactly once after a restore via a `skipPerSetWeightsInitRef` — a restore already has correct, possibly user-edited weights; letting the effect fire would blow them away. Rest-timer duration was changed from `effectiveExercises[currentIdx].progressionStyle[currentSet-1].restSec` to a new persisted `store.lastSetRestSec`, set directly from the just-logged set's own `restSec` at log time — the old formula silently breaks the moment `currentIdx` can point at a *different* exercise than the one whose set was just logged (exactly what happens mid-superset); the new one is a no-op change for the ungrouped case (identical value either way) and correct for the grouped one. `handleBack()` now also clears `exerciseBuffers` (consistent with it already discarding the current exercise's own in-progress flat buffer), and `launchExercise()` checks for an existing stash before doing a fresh init, so resuming a paused workout via "Continue Workout" mid-superset restores correctly instead of losing progress. Extracted `exerciseSetCount()` (`components/workout/utils.ts`) to replace the "progressionStyle length or defaultSets" formula that had been duplicated three times already and was about to become four (one formula, one place).

**AI-dynamic programs need no special handling:** `workout-data` already nulls `supersetGroup` server-side when a prescription drives the session (sub-PR 1), so `sequence` degenerates to plain per-exercise order automatically — the orchestrator has no AI-specific branching of its own.
