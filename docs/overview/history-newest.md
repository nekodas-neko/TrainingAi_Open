## 2026-07-15 — Cloud session cont'd: why Lever 1b's disk size barely moved (docs-only, no code)

Owner ran the full-clear Lever 1b button on-device (screenshots): five in sequence showed 282,256 →
242,256 (two more 20k-capped presses before #551 merged) → mid-nulling with the new "all at once"
confirm dialog ("Null the decoded JSONB on all 242,256 historical rows…") → final state **0 /
307,387 rows carrying `decoded`, 0 B reclaimable**. Then asked two direct questions: "is this
correct? the size didn't change much" and "are we no longer ingesting/saving stuff we don't need?"

**Question 2 first, since it's the scarier one if the answer were no — re-verified directly in the
current code (not from memory), all three ingestion-side levers confirmed still active:**
- Lever 1a: `insertOuraRawSamples` (`adapter.ts:3501`) unconditionally writes `decoded: null` on
  every new row, regardless of what the decoder produced.
- Lever 2: `shouldDropRawTag` whitelist (`route.ts:49`) still drops pure-telemetry tags before insert.
- Lever 3: `step_live_windows` 30-day prune (`adapter.ts:4252-4257`) still fires on every write.

Nothing regressed. New BLE data was never the source of the "size didn't change" observation.

**Question 1 — the real finding, and a genuine gap in what shipped.** The `decodedRows: 0` /
`decodedBytes: 0 B` figures are correct: `getOuraStorageStats` sums `pg_column_size(decoded)` over
live tuples, and every live value really is null now. But the **table-size** column
(`pg_total_relation_size`, what the per-table list shows) barely moved — `oura_raw_samples` 229 MB →
230 MB, even ticked up slightly, despite reclaiming 36–42 MB of *logical* JSONB. Root cause is
Postgres MVCC, not a bug in Lever 1b: `UPDATE … SET decoded = NULL` never shrinks a row in place — it
writes a new tuple and leaves the *old* one (JSONB payload and all) as a dead tuple occupying its page
until vacuumed. Nulling 240k+ rows in one pass creates 240k+ dead tuples. Autovacuum reclaims that
space, but only for **internal reuse** (future BLE ingest can grow into it instead of extending the
file) — it never shrinks the file itself. Only `VACUUM FULL` (or `pg_repack` for a non-locking
variant) physically rewrites the table into a smaller file and gives the space back for real.

**Not built:** the compaction step. Lever 1b was designed and shipped to null the redundant column; it
was never designed to reclaim disk space by itself, and that distinction wasn't made clear enough at
the time. Proposed as **Lever 1c** — an admin-triggered `VACUUM FULL`/`pg_repack` action, gated the
same way as Lever 1b (confirm dialog, deliberate press) since it needs a brief `ACCESS EXCLUSIVE` lock
on the table (likely seconds on ~230 MB) — not built this session, awaiting the owner's decision on
whether/when to add it.

**Documented, not implemented, per instruction ("write up all the documentation about this and merge
to main, I'll have another agent review it"):**

  path).
