# Contributing to TrainingAI

Thanks for helping. This page is everything you need to pick up work and get it merged. The rules
the code must follow are in [`CLAUDE.md`](CLAUDE.md) — short, one line each, with links to the
reasons. It is written for AI agents, but it is the same rulebook for people.

## The app, in two sentences

A personal training and health app whose **only supported runtime is an Android APK** — a WebView
that loads the app from Railway — on a Samsung Galaxy S25 Ultra. The web build exists for
development; when the two behave differently, the device wins.

## Picking up work

- **Work lives in [Issues](https://github.com/nekodas-neko/TrainingAi_Open/issues).** Anything not
  `blocked` is ready. **`next`** marks what the owner wants done first. `good first issue` and
  `help wanted` mark things that are good to start on.
- **Releases go out every Tuesday**, carrying everything merged that week.
- **Claim an issue by opening a draft PR** with `Closes #N` in its description, as soon as you
  start. That is how everyone else sees it is taken.
- **Labels:** `type:` what it is · `area:` which part of the app · `lane: engine` (storage, API,
  native) or `lane: surface` (screens, components) · `blocked` / `needs:` why it is not ready ·
  `re-verify` — check the issue still matches the code before building it.
- **Found a bug or have an idea?** Open an issue with one of the templates. It will be triaged.

## Setting up

```bash
pnpm install          # pnpm only — Railway deploys with a frozen pnpm lockfile
pnpm dev              # the dev server; needs a local Postgres
pnpm test             # the test suite
pnpm check:rules      # the repo's custom checks (one of the five CI gates)
```

Local database and environment: [`docs/local-dev-database.md`](docs/local-dev-database.md) and
[`docs/environment-variables.md`](docs/environment-variables.md).

## Before you open the PR

- Branch from a fresh `main`, named `fix/…`, `feat/…`, `chore/…` or `docs/…` plus a short
  description.
- Read the domain index for the area you are touching: [`docs/domains/`](docs/domains/README.md).
- Check [`docs/module-map.md`](docs/module-map.md) before writing a helper — most things exist.
- Run `pnpm dev` and use what you changed. Passing types and lint is not testing.
- Fill in the PR template, especially **Not exercised**: the things your change could break that
  you could not test (the device, native code, production data).

## What happens to your PR

1. **CI runs five required checks** — Lint, Tests, Build, Migration Check, Custom Rules. All must
   pass; the merge button enforces it.
2. **Review.** Some reviews come from AI agents working through the owner's GitHub account. Their
   comments end with a *Generated by Claude Code* footer — that is how you tell them apart.
3. **The owner merges your PR.** Agents may review and approve it, but never merge a PR they did not
   write.
4. **Merging does not deploy.** Your change reaches users in the next weekly release, which the
   owner approves. See the release notes on the [Releases](https://github.com/nekodas-neko/TrainingAi_Open/releases)
   page.

## Three things that are easy to get wrong here

- **Dates.** The user is in a timezone ten hours from UTC. Never
  `new Date().toISOString().slice(0, 10)` — use `todayInTz()`.
  [`docs/rules/dates-and-timezones.md`](docs/rules/dates-and-timezones.md)
- **Offline-first.** The phone's local database is the source of truth; the server is backup and
  sync. A write updates the local store as well as the server.
  [`docs/rules/offline-first-and-storage.md`](docs/rules/offline-first-and-storage.md)
- **Caches.** Every write clears caches through a named group in `lib/cache-groups.ts`.
  [`docs/rules/cache-invalidation.md`](docs/rules/cache-invalidation.md)
