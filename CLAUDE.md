# TrainingAI — how to work here

Personal training and health app. **The only supported runtime is the APK on the owner's Samsung
Galaxy S25 Ultra**, a WebView loading the app from Railway. Next.js 15 · React 19 · TypeScript ·
Tailwind v4 · Drizzle on Postgres (Railway) · on-device SQLite as the source of truth · Gemini via
`@ai-sdk/google`. Where things live: [`docs/module-map.md`](docs/module-map.md). The eleven areas of
the app and their docs: [`docs/domains/README.md`](docs/domains/README.md).

This file is short on purpose. Each rule below is one line; **the reasons and the incidents behind
it are in the file it points to — read that before working in the area**. The full previous
version is kept verbatim at [`docs/archive/CLAUDE-2026-10-05.md`](docs/archive/CLAUDE-2026-10-05.md).

## How work flows

- **Work is GitHub Issues.** Labels: `type:` (bug · feature · chore · tuning · question ·
  device-check), `area:` (the eleven pillars), `needs:` / `blocked` (why it is not ready),
  `lane: engine` / `lane: surface` (which half of the code), `agent: bugfix` / `agent: implementer`
  (who picks it up), `re-verify`, `hotfix`. Defined in [`.github/labels.yml`](.github/labels.yml).
- **The queue is every ready issue** — not `blocked`, not `needs:`, carrying your `agent:` label.
  Work it in order: **`hotfix`, then `next`, then bugs, then the rest oldest first**. Batch issues of
  the same `area:` and `lane:` that touch the same files into one PR (never a migration). The owner
  steers with the `next` label. A **milestone is the record of a release**, filled at release prep —
  not the plan.
- **Releases are weekly, on Tuesday** ("patch Tuesday"): everything merged that week ships together.
  A hotfix ships off-schedule **only when production is actually broken**.
- **A title says what the task is, in plain words** — for an issue, a PR and a one-off session
  alike. No entry IDs, lane letters or `[area]` tags: labels carry area and lane, and the issue
  number is the ID. **An issue title starts with its type** — `bug:`, `feature:`, `chore:`,
  `tuning:`, `question:`, `device-check:` — kept in step with the `type:` label automatically.
- **A question for the owner is a `type: question` issue**, never a chat message. Write the brief
  into it: recommendation first, why it wins a year out, the alternatives and what each is better
  at, the reversal cost, plain English, under a minute to read.
- **Every change reaches `main` through a PR** with `Closes #N`. Five checks are required — Lint,
  Tests, Build, Migration Check, Custom Rules — and squash is the only merge method. Turn on
  auto-merge when you open the PR. Locally, `pnpm check:rules` runs the Custom Rules job (quote its
  `Ran N of N`) and `pnpm test` the suite; neither alone is the gate.
- **A merge deploys nothing.** Production changes only through a release: a `v*` tag, deployed by
  `.github/workflows/release.yml` after the owner says "approve". Process and recovery:
  [`docs/owner-manual.md`](docs/owner-manual.md).
- **Who merges:** the Orchestrator merges agent PRs on green CI. **Never merge a PR we did not
  author** — review, comment, approve; the merge is the author's or the owner's.
- **Branches:** `fix/`, `feat/`, `chore/`, `docs/`, `security/` + a kebab-case description. **The
  word `claude` never appears in a branch name.** Start from a freshly fetched `main`.
- **Commit messages say why, read as a human engineer's, and carry no AI attribution** — no session
  URLs, no "generated by". Never `--no-verify`, never force-push, never `reset --hard` without the
  owner's say-so.
- **User-visible change:** bump `package.json` and add a `packages/shared/src/changelog.ts` entry at
  release prep, not per PR — the Orchestrator does it once per release.

## The agents

Three, plus one mode — full contract in [`docs/agents/README.md`](docs/agents/README.md):
**🪐 Orchestrator** (cloud: triage, owner questions, release prep, merges) · **🪲 BugFix** (cloud:
reports → issues, small fixes) · **🚧 Implementer** (the owner's machine: works the queue,
device checks) ↳ **release-test mode**. Work out which you are first. One session per role, kept
open; compaction is automatic (launch with a small `--autocompact` window), so **write each task's
outcome to its issue or PR** — that is what survives it. Titles end 🟢 while live, 🔴 when wrapped.

## Before you build

- **Read the issue, then re-verify its premise against `main`** — mandatory for `re-verify`.
- **Check [`docs/module-map.md`](docs/module-map.md) before writing any helper or formula.** Domain
  math lives once, mostly in `packages/shared/src/`; two implementations of a metric is a bug.
- **A change that visibly rearranges a daily-use screen needs a mockup and the owner's yes first**,
  shown at the real 384 px dark viewport.
- **Test on `pnpm dev` before opening the PR**, exercising every changed route and flow. Green
  types and lint are not testing. Local database:
  [`docs/local-dev-database.md`](docs/local-dev-database.md).

## Code rules — one line each, reasons in the linked file

**Dates and time** → [`docs/rules/dates-and-timezones.md`](docs/rules/dates-and-timezones.md)
- Never `new Date().toISOString().slice(0,10)`; "today" is `todayInTz()` from
  `packages/shared/src/date-utils.ts`. A clock time is `formatTimeOfDay(at, tz)`, never a bare
  `toLocale*String`.
- Windows start at the user's local midnight, never `now − N×86400000`; `aestMidnight` always gets
  its timezone argument. Date params go through `normalizeDateParam`, and their Zod regex accepts
  both `-` and `/`.
- A test never hardcodes one side of a rolling window, and anchors fixtures to local midday.

**Cache** → [`docs/rules/cache-invalidation.md`](docs/rules/cache-invalidation.md)
- Every write invalidates through a named group in `lib/cache-groups.ts`; never a hand-rolled key
  list. A component reads cached data with `useCachedValue` (`lib/hooks/use-cached-value.ts`).
- One TTL per key, defined in `packages/shared/src/cache-ttl.ts`; one fetch variant per key.
  "Today" keys embed the local date. API responses are `private, no-store`.

**Offline-first and storage** → [`docs/rules/offline-first-and-storage.md`](docs/rules/offline-first-and-storage.md)
- The on-device local store (`lib/local-store/`) is the source of truth. A domain that writes
  locally reads locally, and every write to it — deletes included — updates the local store.
- A server hard delete is invisible to unsynced devices: delete UI needs a `deleted_at` tombstone.
- A migration that adds or drops a table or column regenerates `lib/data/postgres/claude-ro-views.sql`
  with `scripts/generate-claude-ro-views.js` (reads `LOCAL_DATABASE_URL`) in the same PR. Name
  migrations with `scripts/next-schema-number.js`.
- Keep the pool's error handler and timeouts in `lib/data/postgres/client.ts`.

**Oura BLE** → [`docs/rules/oura-ble.md`](docs/rules/oura-ble.md) and
[`docs/oura-ble-operations.md`](docs/oura-ble-operations.md)
- Byte layouts come from the `open_oura` source, never memory. Decoders never throw. The history
  cursor advances only past server-acknowledged events. Never prune or mutate the server raw
  archive. Never re-onboard the official Oura app. The Oura Cloud integration is gone for good.

**AI, security, integrations** → [`docs/rules/ai-security-and-integrations.md`](docs/rules/ai-security-and-integrations.md)
- Structured LLM output uses a schema, never `JSON.parse` of text; no model-reported number gates
  an action or is shown as fact; prose routes use `lib/ai/prompt-guards.ts`.
- Security fails closed. Never pass a request body into `.set()`; check affected-row counts;
  ownership-verify client-supplied ids. New ingest and AI routes get Zod and a rate limit at birth.
- Read external field names from the pinned source and prove a non-null value lands in the DB.
- Never hardcode session names or training structure; identity is the DB id.

**Mobile and runtime** → [`docs/rules/mobile-and-runtime.md`](docs/rules/mobile-and-runtime.md) and
[`docs/mobile-ui-and-performance.md`](docs/mobile-ui-and-performance.md)
- Bottom-anchored controls use a floored safe-area utility (`pb-safe-action`), never bare `pb-safe`.
- A repeat visit never flashes a skeleton: seed from cache synchronously, revalidate behind it.
- The web build is a dev surface and stays logic-free; when they differ, the device wins.
- **Never uninstall the app or install over it with a differently signed APK** — it destroys the
  ring's BLE key, which cannot be recovered. **Never point the real app at a local server.**
  [`docs/canonical-runtime-android.md`](docs/canonical-runtime-android.md).

**Git, safety, packages** → [`docs/rules/git-safety-and-packages.md`](docs/rules/git-safety-and-packages.md)
- `pnpm` only; commit `package.json` and `pnpm-lock.yaml` together.
- Production data: adding and backfilling are allowed with a verified snapshot first; **anything
  that deletes data, or touches auth, sessions, secrets or money, is confirm-first, every time.**
- Never commit secrets. Check `.git/shallow` first when a merge misbehaves
  ([`docs/git-sandbox-investigations.md`](docs/git-sandbox-investigations.md)).

**Working practices** → [`docs/rules/working-practices.md`](docs/rules/working-practices.md)
- Structural calls are yours: decide, write down why, continue. The owner's are data destruction,
  money, auth and secrets, scoring calibration, and genuine product preference.
- Scoring changes are a `type: tuning` proposal stating how many past days move; never shipped
  without the owner's sign-off.
- Verify with the tool that owns the question (`get_check_runs`, the parser, `git diff`), never with
  a grep you wrote. Never call something fixed from intent.
- When presenting work, **name the failure surfaces you did not exercise** — native SQLite,
  Capacitor plugins, safe-area, real device tokens, production data. Device-dependent changes get
  the device check ([`docs/device-smoke-checklist.md`](docs/device-smoke-checklist.md)) or say
  plainly they have not had it.
- A finding you do not fix becomes an issue in the same session. Fix a pattern on every surface
  that has it, not just the one you were looking at.
